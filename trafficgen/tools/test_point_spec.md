# 测试点细化规范（所有模块通用）

## 目标
将已枚举的场景逐一细化为**原子测试点**，作为编写真实测试的蓝图。
每个场景若有 正例/异常/分支 变体，必须为每个变体生成**并列的**测试点。

## 输出格式（每个测试点一行 Markdown 表格）

| 测试点ID | 覆盖场景 | 测试函数名 | 输入 | 断言(可观测) | 类型 | 备注 |

字段说明：
- **测试点ID**: `<场景tag>-POS` / `-NEG` / `-BR1` / `-BR2`（正例/异常/分支1/分支2）。如 `E1-POS`、`E25-NEG`、`P1-BR1`。
- **覆盖场景**: 枚举中的场景 tag（如 `E1`、`AUTH1`、`P1`）。
- **测试函数名**: 合法的 Go 测试函数名，如 `TestNewEngine_ZeroConfig`。
- **输入**: 具体输入值/构造方式。
- **断言(可观测)**: 必须断言**可观测的结果值或行为**，不能只写"不 panic"或"对象存在"。未被赋值的字段恒为零值会通过任何结构性断言——必须断言真实值。
- **类型**: 三选一（见下）。
- **备注**: MANUAL 类型写明原因+具体手动测试命令；REAL/SIMULATED 写注意事项。

## 类型分类（对应用户 4 项要求 #2 #3）

| 类型 | 含义 | 何时用 |
|------|------|--------|
| **真实(REAL)** | 可用 `go test -race` + `go vet` 全自动验证，断言真实行为 | 纯逻辑/内存/数据结构/状态机/校验/序列化/解析——绝大多数单元与集成测试 |
| **模拟(SIMULATED)** | 用内存 fake/stub 模拟依赖（如假网卡、假 GORM、假时间），仍用 -race/vet 自动跑 | 依赖外部但可在进程内模拟：DB 用 SQLite 内存库、Writer 用 bytes.Buffer、时间用注入接口 |
| **手动(MANUAL)** | **无法**自动化——依赖真实 NIC/内核/硬件/抓包，必须由用户执行 | 真实发包到物理网卡、真实 PPS/BPS 限速精度、内核 AF_PACKET 行为、多队列、真实 PCAP 回放到线缆 |

### MANUAL 类型的强制要求
对每个 MANUAL 测试点，备注中必须包含：
1. **为何无法自动测**（依赖什么物理资源/内核行为）
2. **具体手动测试命令**（tcpdump/scapy/ethtool/ip/iperf3 等完整命令）
3. **预期可观测结果**（抓包应看到什么、计数器应为多少）

## 绑定规则（来自 CLAUDE.md Testing Policy）
1. **断言可观测结果**，非"不 panic"。零值字段必须显式断言非零。
2. **覆盖失败路径**：每个场景正例 + 异常（无效输入/缺失依赖/中途坏状态/空零边界）。
3. **一个代码路径一个测试**：函数有 N 个分支就 N 个测试点，不能测 A 假设 B 工作。
4. **集成测试**：跨层路径（API→引擎→输出 / planner→worker→writer）要有端到端测试点。
5. **并发正确性**：共享状态/共享速率组件，测试点必须测 N worker 下的**聚合可观测行为**（实际总吞吐 vs 配置速率），而非仅 -race 无竞争。
6. **失败测试先行**：对应 bug 修复的场景，测试点应先复现 bug（断言坏行为）再断言修复后行为。
7. **真实环境分类**：REAL/SIMULATED/MANUAL 必须标注，MANUAL 必须给命令。
