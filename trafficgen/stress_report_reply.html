报告项根因修复与验证
BUG-01
已修复		10-14 晚"UDP 拆包"改动中，同一份数据报的多个分片共用了一份内部记录表；发送端写、构建端读，并发下必然相撞。124 并发只是把碰撞窗口变成了必现。改为每个分片独立记录。用你们的 124 并发配置重放：102 个任务受理、22 个被"同时最多 100 任务"的保护上限正常拒绝（这个上限是既有设计）、零崩溃。另核点了你们堆栈里提到的另一处嫌疑位置——反汇编证实那处全程有锁，不是它。
BUG-02
已修复		服务异常退出后，卡在"进行中/排队"状态的任务没有任何启动期纠正机制。服务启动时统一把残留任务标为失败并注明"interrupted by server restart"。已用你们报告里那两个卡死的任务（B1REPRO-16/25）实证：B1REPRO-25 已被标为失败并带原因；B1REPRO-16 显示 stopped 是你们当时手动停止生效的结果（停止接口当时返回 null 是因为引擎队列里已经没有它，数据库状态其实已翻转）。
BUG-07
已修复		三个真实缺陷：①批量任务里每个分项省略 config 时产出乱码报错；②工具说明文字在线上被截断——这是我们在 10-13 一轮修复中引入的回归（文字里嵌了未转义的引号）；③那段说明写错了形状（说了不存在的 type=synth）。三项全修：省略 config 现在按"全默认"处理正常建单；说明文字重写为真实形状并附完整示例；联同把校验口径补齐。线上实测两种形状（带 config / 省略 config）都能正常建单跑包。
BUG-04

BUG-16

02核实后无需改代码的项（对等说明 + 一处待补）

BUG-08数量控制只有三种：条数（flows）、速率（bps）、时长（time）。"按包数"这个类型在全部历史版本中都不存在，不是被移除的。省略时不写即默认"1 条流"——三种类型已在工具参数说明里写明；"省略时默认 1 条"这句话此前只在另一层文档里，现已补进工具参数说明。若"按包数控制"是真实需求，欢迎提需求单。
BUG-10对齐一下两条事实：同名任务在"仍在运行"时提交会被拒（防重复护栏）；同名任务已结束后新建是允许的（每次新建都是新任务）。这是两个不同操作的两条规则，并存不矛盾。此前这套语义从未书面声明，是我们的文档缺口，已登记补充。另外说明：并发下如果同一任务被同时启动，会收到"请重试"类错误，属于正常竞态保护。
BUG-06七个协议里其实都没有名为 method 的字段——各协议控制动作的字段各不相同（ssh 叫 scenario、s7 叫 commands、isis 叫 pdu_type 等），这些字段都真实存在且生效。真正的问题是：这些字段的取值列表在任何查询面上都看不到（说明文字是空的）——这是我们的文档缺口，已登记补全。tls 的 alpn/cert 属于 tls 层，放在 http 层会被正确拒绝。
BUG-15
超出本轮范围		本轮开发与测试的唯一口径是开发环境 8081——报告的全部测试对象与结论都基于它，全部有效，与本条无关。8082/8086 是同机器上另一套安装版实例（发布包装的旧版本），不属于开发环境，其版本状态不影响任何一轮测试结论，也无需复测——它随正式发版流程自然对齐，与开发迭代解耦。

04性能三项：确认存在，单独立项

BUG-12确认。引擎并行为 8 个打包线程 + 1 个调度（配置默认，无隐藏限制）；40×8 秒任务的消化效率需专项分析（time 型任务的推进效率、队列策略），已立项性能专项。
