### 1.1 HTTP 头部默认值统一规则（上一会话完成）

**规则：用户给的 > 默认值（按场景联动） > 不加**，所有头部（请求+响应）统一。

**请求侧**（`trafficgen/internal/protocol/http/http.go` 的 `buildHTTPRequest`）：
- `Method`：空 -> `"GET"`
- `URI`：空 -> `"/"`
- `Version`：空 -> `"HTTP/1.1"`
- `Host`：用户没给 -> `dstIP`（IPv6 自动加 `[]` 括号，`bracketHost`）
- `Content-Length`：用户没给 + Body 非空 -> `len(Body)`
- `Connection`：用户没给 -> `Transactions>1` 或 `KeepAlive=true` -> `keep-alive`，否则 `close`

**响应侧**（`buildHTTPResponse`）：
- `Version` / `StatusCode`(默认200) / `StatusText`（按 RFC 7231 表查，未知 -> `"Status NNN"`）
- `Content-Type`：默认 `text/plain`（body 非空时）
- `Content-Length`：默认 `len(ResponseBody)`（body 非空时）
- `Connection`：同请求侧

**HTTPConfig 结构体**（`trafficgen/internal/core/types.go`）：
- `Headers` 已重命名为 `RequestHeaders`（JSON key: `request_headers`）
- 新增 `Version` / `ResponseHeaders` / `ResponseBody` / `ResponseStatusCode` / `ResponseStatusText`
- **向后兼容**：`strategy_convert.go` 里 `request_headers` 为空时 fallback 读旧 key `headers`

### 1.2 L2/L3/L4 字段默认值（上一会话完成）

**所有默认值集中在 `mapToFlowSpec`**（`trafficgen/internal/core/strategy_convert.go`），统一规则：
```
用户给的（含显式 0/空字符串/null） > 默认值 > 不加
```

存在性检查 helper：`v, ok := cfg[key]; ok && v != nil` —— 区分「未给」和「显式 0/空」。因为 `dscp:0`（best-effort）、`flags:0`（允许分片）、`src_port:0` 都是合法的用户选择，不能被 `getIntDefault` 吞掉。

**默认值表**：

| 字段 | 默认值 | 说明 |
|------|--------|------|
| `SrcMAC` | `02:00:00:00:00:01` | IEEE 802 本地管理 MAC（trafficgen 标记） |
| `DstMAC` | `02:00:00:00:00:02` | 同上 |
| `SrcIP` | `192.0.2.1` | TEST-NET-1（RFC 5737），公网丢弃不泄漏 |
| `DstIP` | `192.0.2.2` | TEST-NET-1 |
| `SrcPort` | `12345` | 高位非特权端口 |
| `DstPort` | `80` | TCP/UDP/HTTP 默认；DNS 自动覆盖为 53 |
| `TTL` | `64` | 原有 |
| `DSCP` | `0x2E` (EF, TOS byte `0xb8`) | trafficgen 包标记 |
| `ECN` | `0` | 原有 |
| `Flags` | `0x02` (DF=1) | 对齐现代 OS TCP 默认 |
| `FragOffset` | `0` | 原有 |

**关键修复**：`builder.go` 的 `L3Base` 删除了旧的 `if flags==0 { flags=DF }` 默认逻辑——默认值现在只由 `mapToFlowSpec` 负责，`L3Base` 原样透传 `spec.Flags`，否则用户的显式 `flags:0` 会被静默改写。

**batch 路径修复**（`worker.go` processBatchTask）：`tupleGen.Next()` 返回空值时不再无脑覆盖 `mapToFlowSpec` 已填好的默认值，改成条件覆盖（`if srcIP != "" {...}` 等）。

## 2. 当前问题：TCP 抓包乱序（未修复，接手任务）

### 2.1 现象

用户在 Wireshark 抓包看到（`/tmp/企业微信截图_20260718225103.png`）：
- `[TCP Retransmission]`（FIN-ACK seq=0 ack=0）
- `[TCP Port numbers reused]`（同一 4-tuple 出现新 SYN）
- `[TCP Out-Of-Order]`
- `[TCP ACKed unseen segment]`

tcpdump 抓包同样看到 IP ID 乱序（9,4,6,7,1,5,3,8,2 而非 1,2,...,9）。

### 2.2 已确认的事实（重要！）

1. **引擎已有 shard 路由机制**（`engine.go` + `worker.go` + `shard_router.go`）：
   - `computeHashKey` Case 3 已经是**无序 4-tuple**（min/max 排序后拼接）——即**「同源 IP 和目的 IP（不论方向）路由到相同 worker」已经是现状**！
   - 测试 `TestComputeHashKeyBidirectionalSameKey`（`shard_router_test.go:37`）已验证双向同 key
   - 路由链路：`ConfigWorker -> shardedConfigChan[i] -> PacketWorker[i] -> shardedPacketChan[i] -> OutputWorker[i]`，同一 flow 的所有包进同一 shard，单 goroutine FIFO

2. **用户要求"同源 ip 和目的 ip（不论方向）都路由到相同的 worker"——不需要改 shard 路由，已经是这样。**

### 2.3 未确认的疑点（接手要查）

抓包乱序说明同一 flow 的包在**某个环节**失序。可能断点：

1. **ConfigWorker 多 worker 并发**：多个 ConfigWorker 并行处理多个 flow，虽然每个 flow 单独 FIFO，但**同一 4-tuple 的多条 flow（用户多次发任务/一个任务多个 flow）会哈希到同一个 shard**，包交错进入 shard channel——TCP 层面这是不同连接的包，但 Wireshark 按 4-tuple 归并成一条流就乱了。

2. **HTTP planner 的 goroutine**：`http.go` 的 Plan 是 `go func()` 里顺序 push 到 `configChan`，ConfigWorker 从 `configChan` range 读。**单 flow 内顺序应该保住**——除非 ConfigWorker 的 `select` 分发（`case w.engine.shardedConfigChan[shardIdx] <- config`）在多 flow 并发时交错。

3. **复现方式**（务必先复现再改）：
   ```bash
   cd trafficgen && ./bin/trafficgen -config configs/config.dev.yaml &
   # 登录拿 token（admin/admin）
   # 创建 HTTP 策略（最小 config），创建任务，start
   # tcpdump -i enp135s0f0np0 -nn -vv -S 'tcp and host 192.0.2.2'
   ```
   观察：单任务单 flow 时包序是否正常（IP ID 应 1,2,...,9 递增）；多个任务并发时是否乱。

4. **核心问题**：用户看到 FIN-ACK seq=0 ack=0 —— 这更像**同 4-tuple 多条连接的包交错**（Wireshark 把不同连接的包当成一条流）而非单 flow 内部乱序。单 flow 内部乱序的话 seq 应该是连续的（1000,1001,1058...），IP ID 才乱。

### 2.4 建议排查顺序

1. **单任务单 flow 抓包**：确认 IP ID 是否 1..9 递增。若是 -> 单 flow FIFO 正常，问题在跨连接交错。
2. **多任务并发抓包**：确认是否交错。若是 -> 需要按「连接」区分而不是按 4-tuple（因为多条连接同 4-tuple 时 Wireshark 必然误判）。
3. **可能的修复方向**（待确认，不要直接改）：
   - 多 flow 时 src_port 递增（模拟真实客户端 ephemeral port），让每条连接的 4-tuple 不同
   - 或 batch 路径用 `group_id` 给每条连接不同 shard（但同 4-tuple 还是会被 Wireshark 归并，治标不治本）
   - 本质：**同 4-tuple 的多条 TCP 连接在 Wireshark 里必然被当成一条流**，最干净的解法是让 src_port 每连接不同（真实客户端行为）
