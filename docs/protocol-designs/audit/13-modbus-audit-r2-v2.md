## 3. CRITICAL 问题

### R2-C1：S14/T-053b 响应 PDU `19 01` 算术错误——`0x99 | 0x80 = 0x99`，不是 `0x19`

**位置**：§6.14（第 956-961 行）；§7.5 T-053b（第 1081 行）；§7.12 T-101 参照（第 1171 行）；§11.2 修复清单 R1-H1 行（第 1607 行）。

**问题**：v2.0.1 为 R1-H1 新增的豁免场景（FC=0x99 + ExceptionCode=0x01）断言响应 PDU 为：

```
19 01   -- 文档写 FC=0x19 (0x99|0x80)
```

但 `0x99 | 0x80 = 0x99`（0x99 的 bit7 已经是 1，OR 后不变）。**`0x19` 是 `0x99 & 0x7F`（去高位）的结果，不是 `0x99 | 0x80` 的结果**。

实际响应 PDU 应为 `99 01`（功能码 0x99 + 异常码 0x01），或按"异常响应 = 原码 OR 0x80"不变式 §1.4 第 4 条，字节序列为 `99 01`。

**影响**：这是 R1-H1 豁免规则（§8.1）唯一正向验证用例。照此断言实现，planner 若按 `FC | 0x80` 生成（正确）则测试失败；若实现者按"去掉 bit7"或 `& 0x7F` 生成 `0x19` 以"匹配测试"，则生成错误 wire 格式——测试反而教坏实现。S14 场景（§6.14）同样错误，且 T-025 的 `C1 01`（0x41|0x80=0xC1 ✓）与本节自相矛盾：文档正确计算 0x41 的高位叠加，却在 0x99 上算错。

**依据**：MB-ASYM-TCP §7 Exception Response（"The function code field of the response = function code of the request + 0x80"）；§1.4 不变式 4 自身。

**修复建议**：S14 响应改 `99 01`（解释：0x99|0x80=0x99，bit7 已置位故不变）；T-053b 预期响应 PDU 改 `99 01`；§11.2 R1-H1 行同步。注意 §8.1 高位豁免条款表述"FC=0x99 bit7=1 + ExcCode=0x01 → 通过"仍成立，但需补充说明：此时"FC|0x80"在数值上等于 FC 本身（幂等），异常响应与请求功能码字节相同——这是该豁免的独特语义，应显式声明并测试。

### R2-C2：FC 0x2B 响应 PDU 结构完全未规格化，T-024/T-122~T-125 断言无规格支撑

**位置**：§3.3.17（第 436-455 行）；§7.2 T-024（第 1034 行）；§7.16 T-122~T-125（第 1213-1216 行）；§8.4 FC 0x2B 行（第 1353 行）；§10.6 已知坑（无 0x2B 响应相关条目）。

**问题**：§3.3.17 仅给出请求 PDU 表（FC + MEI Type + Read Device ID Code + Object ID），**响应 PDU 只写了一句"与 MEI Type 相关，本设计 v2 仅支持 0x0D（Read Device Identification）基础子集"——没有响应字节表**。

依据 MB-ASYM-TCP §6.21（Encapsulated Interface Transport / Read Device Identification），FC 0x2B 响应 PDU 为：

| 字节 | 字段 |
|------|------|
| 0 | FC = 0x2B |
| 1 | MEI Type = 0x0D |
| 2 | Read Device ID Code（回显请求值） |
| 3 | Conformity Level（0x01=basic, 0x02=regular, 0x03=extended, 0x81/0x82/0x83=带更多对象） |
| 4 | More Follows（0x00/0xFF） |
| 5 | Next Object ID |
| 6 | Number of Objects |
| 7.. | Object(s)：Object ID(1) + Object Length(1) + Object Value(N) |

文档 T-024 断言响应为 `2B 0D 01 00 01 <vendor 字符串>`——按上述规范，响应第 3 字节是 Conformity Level 而非"01"后直接跟数据；第 4 字节 More Follows、第 5 字节 Next Object ID、第 6 字节对象数等字段**全部缺失**。若按规范结构，基础响应至少为 `2B 0D <code> <conf> <more> <next> <count> <objID> <len> <val>`（9+ 字节），T-024 的 7 字节序列与规范不兼容。

**影响**：实现者无响应格式可循；T-122~T-125 声称"响应含 vendor/product/version 等基础对象"但未定义对象字段布局，无法断言；Wireshark 对 FC 0x2B 的解析（§7.7 T-073~T-080 未覆盖 0x2B）依赖正确结构。

**修复建议**：§3.3.17 增加 FC 0x2B 响应 PDU 完整字节表（MEI + Code + Conformity + More Follows + Next Object ID + Number of Objects + Object 三元组）；§7.2 T-024 与 §7.16 T-122~T-125 按该表重写断言（或明确"响应由 ResponseValues 注入，planner 不自动构造"并给出完整示例）；§8.4 FC 0x2B 行从 "MEI 特定 —" 补为长度公式。

## 4. HIGH 问题

### R2-H1：§8.1 FC 0x08 子功能上限 0x0018 与规范不符（应为 0x0013）

**位置**：§8.1（第 1305 行）；§3.3.6（第 232 行）；§7.17 T-126~T-130。

**问题**：§8.1 "SubFunction (FC=0x08) | 0x0000-0x0018"；§3.3.6 请求表"子功能码 0x0000-0x0018"。

MB-ASYM-TCP §6.8（Diagnostics）定义的诊断子功能码最高为 **0x0013**（Return IOP Overrun Count）。完整列表：0x0000-0x0004、0x000A-0x0013（0x0005-0x0009 保留）。**0x0018 不是规范定义的子功能码**。

**影响**：Validate 接受 0x0014-0x0018 的值，但规范无这些子功能定义；实现者可能在文档指引下生成规范外报文。

**修复建议**：§3.3.6 与 §8.1 改为 0x0000-0x0013（并注明 0x0005-0x0009 保留）；如设计有意扩展接受范围，须显式声明"接受 0x0000-0x0013，其余拒绝"或标注扩展理由。

### R2-H2：T-064/T-108 断言不可执行——ResponseValues 无法"试图覆盖请求"

**位置**：§7.5 T-064（第 1096 行）；§7.12 T-108（第 1178 行）；对照 §5.2 ResponseValues 定义（第 667-678 行）。

**问题**：两条用例描述为：

> T-064 | ResponseValues 覆盖请求 PDU | FC=0x03, Values 设置但 ResponseValues 试图覆盖请求 | "response_values only applies to response PDU"
> T-108 | ResponseValues 覆盖请求 PDU | ... | 拒绝（ResponseValues 仅作用于响应）

但 §5.2 定义的 ResponseValues 是**独立字段**（`response_values` json tag），它只作用于响应 PDU——不存在任何配置输入能让 ResponseValues"试图覆盖请求"：请求 PDU 由 Values 字段（`values`）决定，ResponseValues 与请求无任何交互路径。`"response_values only applies to response PDU"` 这条错误消息在现有字段设计中**不可能被触发**。

**影响**：两条用例断言一个不可达的错误路径——照此实现，要么实现一个无处调用的校验分支（死代码），要么测试无法构造该场景而跳过。这是 CLAUDE.md §Testing Policy 规则 3（测试正确的作用域/路径）的反例。

**修复建议**：删除 T-064/T-108，或将设计改为"ResponseValues 非空时若 FC 语义上不产生响应（如广播+SuppressBroadcast）则拒绝"并重写断言；或在 §5.2 明确 ResponseValues 与 Values 完全独立、无互斥交互，删除"覆盖请求"表述。

## 5. MEDIUM 问题

### R2-M1：T-024b 只验证公式语义、不验证实现公式——CLAUDE.md 规则 5 反例

**位置**：§7.2 T-024b（第 1035 行）；§3.3.14（第 383-387 行）。

**问题**：T-024b 描述"wire 为 echo `16 0000 00FF 0001`；按公式与 Cur=0x1234 计算得 0x0034（公式语义验证，非 wire 断言）"。用例的**可断言部分只有 echo 字节序列**（与 T-022/T-116 重复），而"公式算术结果 0x0034"是文档文本中的手算，**没有任何实现代码执行该公式**（§3.3.14 明确"实现不执行该公式"）——测试无从断言 0x0034，该算术验证不落在任何被测代码上。

**影响**：这是 R1-C6 修复声明"新增 T-024b 验证公式"的核心用例，但它验证的是文档文本而非实现。若后续实现引入公式（如 v3 模拟寄存器状态），无测试守护；若实现不引入公式，T-024b 与 T-116 完全等价（重复用例）。

**修复建议**：将 T-024b 改写为"公式实现级测试"（若实现含公式，则断言 (Cur AND A) OR (O AND ~A) 计算器函数的输出；若不含，删除该用例并将公式保留为纯文档说明，标注"无对应实现测试"）。二选一，避免"语义验证"悬空。

### R2-M2：§8.4 FC 0x14 长度公式与 R1-C5 修复后的 item 结构矛盾（残留）

**位置**：§8.4（第 1348 行）。

**问题**：§8.4 FC 0x14 行写：

> 0x14 | 1 + Σ(item 长度) | ByteCount + items；每 item 长度 = 2 + Record Length × 2（RefType + item 内 ByteCount + Record Data）

公式"1 + Σ(item 长度)"中 item 长度 = 2 + 2×RL，则 ResponseValues 总长 = 1 + Σ(2+2×RL)。但 FC 0x14 响应 PDU = FC(1) + ByteCount(1) + items，ResponseValues 是"FC 之后的字节"（§5.2 定义），即 ByteCount(1) + items，总长 = 1 + Σ(2+2×RL)。**文本行"1 + Σ(item 长度)"把 ResponseValues 的长度算成了整 PDU 长度**（多算了 FC 自身 1 字节？不——恰相反：公式文字与 §5.2 的"bytes after FC"定义歧义）。

对照 T-115：响应 `14 06 06 04 1234 5678`，ResponseValues = `06 06 04 12 34 56 78` = 7 字节 = 1(ByteCount) + 1 个 item(2+2×2=6)。按 §8.4 公式 1 + Σ(2+2×RL) = 1+6 = 7 ✓ 数值碰巧对。但若按"1 + Σ(item 长度)"字面理解（把 ByteCount 也算进 PDU），与 §8.4 其它行（如 0x03: "1 + Quantity*2" 指 ByteCount+寄存器值）语义不一致——§8.4 所有其它行的长度都**含 ByteCount 的 1**，FC 0x14 行也含（"1 + Σ"），但 **0x15 行写 "= 请求 PDU 长度"（含 FC）**，0x0C 行写 "1 + 6 + N"（含 ByteCount），0x18 行 "2 + 2 + FIFOCount*2"（含 ByteCount 2 字节）。

真正的问题：§8.4 表头声称"ResponseValues 长度"（= FC 之后的字节），但 **0x15 行 "= 请求 PDU 长度" 是按含 FC 的整 PDU 计算**（请求 PDU = FC + ByteCount + items，FC 0x15 响应 echo 整 PDU）。若 ResponseValues 语义为"FC 之后的字节"，FC 0x15 的 ResponseValues 应为 PDU 减去 FC 1 字节；若为整 PDU，则其它行都少算 1。**全文未定义 FC 0x15 的 ResponseValues 是否含 FC**，T-021 断言"响应同请求（echo）"但 ResponseValues 未在 T-021 中使用（FC 0x15 响应 echo 由 planner 自动构造？还是需 ResponseValues 提供？）——§5.2 FC 0x15 的 ResponseValues 说明空白。

**修复建议**：§8.4 表头注明"以下长度均为 FC 之后字节（不含 FC）"；FC 0x15 行改为 "1 + Σ(item 长度) = 1 + Σ(7+2×RL)"（ByteCount + items）；明确 FC 0x15 响应 echo 时 ResponseValues 是否可选/必填；T-021 补 ResponseValues 说明。

### R2-M3：§6.13 S13 与 §2.6 的 PDU 上限 253 边界核算——253 恰好等于 PDU 上限，需显式声明合法

**位置**：§6.13（第 945 行）；§2.6（第 128 行）；§1.4 不变式 3（第 49 行）。

**问题**：S13 响应 Length=253，PDU = FC(1)+ByteCount(1)+250 = **252 字节**，Length = 1+252 = 253。§2.6 声明"PDU 最大 253 字节"——此处 PDU=252 ≤ 253 合法，Length=253 ≤ 254 上限 ✓，**数值自洽**。

但注意边界语义：FC 0x03 最大 quantity=125 → PDU=252，若再叠加 1 字节（如 FC 0x14 响应加 item 内 ByteCount 前），会逼近/超过 253。文档 §2.6 的"quantity≤123 写多寄存器、≤1968 写多线圈"推导（"由 PDU 长度反推"）未给出推导过程，且 FC 0x10 的 quantity=123 → PDU = 1+2+2+1+246 = 252 ✓ 恰好同界。**无任何用例验证"PDU=253 恰好合法 / PDU=254 恰好非法"的边界**（T-003/T-007 只验证 byte count 250，未断言 Length=253 是上限合法值）。若实现用 `if len(PDU) > 253` 检查，S13 是唯一覆盖 252→253 跳变的场景——测试应显式断言"Length=0x00FD 合法且是上限值"。

**修复建议**：T-007（FC=0x03 qty=125）补充断言：响应 Length=0x00FD=253 且 PDU=252 字节（合法上限）；§2.6 增加 1 行"PDU=253 合法、254 非法"边界断言用例（如 FC 0x10 qty=123 的 Length=253 验证）。

---

### R2-M4：T-019（FC 0x11）响应 Additional Data 长度与 T-076 的 tshark 验证不一致

**位置**：§7.2 T-019（第 1029 行）；§7.7 T-076（第 1121 行）；§6.8 S8（第 853-859 行）。

**问题**：S8 响应 `11 03 01 FF AA BB`（ByteCount=3，Additional=2 字节）；T-019 响应 PDU `11 03 01 FF AA`（ByteCount=3，**Additional=1 字节**）。两处 Additional 长度不同（S8=2、T-019=1），虽然都是合法序列，但同一文档内 FC 0x11 的两个示例不一致——ByteCount=3 与后续字节数（1+1+1=3）各自自洽 ✓，属于风格不一致而非算术错误。

更实质的问题：§3.3.11 的"典型响应示例"（第 325-327 行）给出 `11 02 11 00` 与 `11 04 01 FF AA BB` 两组示例（ByteCount=2/4），与 S8（ByteCount=3）和 T-019（ByteCount=3）**三处四个不同示例**，无一致性说明。

**影响**：低（wire 均合法），但文档内部示例冗余不一致，实现者无法判断"标准示例"。

**修复建议**：统一为一种默认结构（如 ByteCount=3, SlaveID=1, RunInd=0xFF, Additional=1 字节），或标注示例的配置来源（如"T-019 设 ResponseValues=[0x03,0x01,0xFF,0xAA]"）。

### R2-M5：T-112b 断言与 §8.2 FC 0x14/0x15 步进规则不自洽

**位置**：§7.13 T-112b（第 1188 行）；§8.2（第 1322 行）。

**问题**：T-112b 描述"FC=0x14, 2 items 中一个 RecLen=0 | Validate 拒绝（planner 按每 7 字节步进解析 item，RecLen=0 使 item 长度为 0，非法）"。

按 §8.2：FC 0x14 请求 item **固定 7 字节**（每 7 字节步进一个 item），FC 0x14 的 item 内 Record Length 字段（偏移 5-6）**不影响 item 总长**（请求 item 无 Record Data）。因此"RecLen=0 使 item 长度为 0"的说法与 FC 0x14 固定 7 字节规则矛盾——RecLen=0 时 FC 0x14 请求 item 仍是 7 字节（合法，表示读 0 个寄存器？规范中 Record Length 最小 1，0 语义非法但结构合法）。若 T-112b 想测"RecLen=0 拒绝"，拒绝的应是**语义**（Record Length 必须 ≥1）而非"item 长度为 0"；若想测结构非法，FC 0x14 请求没有结构非法的 item 形态（固定 7 字节）。

**修复建议**：T-112b 改为明确语义校验：FC 0x14/0x15 item 中 Record Length=0 → Validate 拒绝（"record length must be >= 1"）；或删除该用例并补 FC 0x15 的 RecLen 校验用例（FC 0x15 动态步进时 RecLen=0 → item 长度 7，可结构合法）。

### R2-M6：T-066d 断言 `17 0000 000A 0003 0003 06 ...` 中 WriteAddress=3 与 StartingAddress+WriteQuantity 语义（起始地址+数量）混用

**位置**：§7.5 T-066d（第 1101 行）；§5.2（第 640-643 行）。

**问题**：T-066d 断言 WriteAddress 回退为 StartingAddress+WriteQuantity=3，请求 PDU `17 0000 000A 0003 0003 06 ...`。回退公式本身在 R1-H3 已修复 ✓，但该公式语义上"写起始地址 = 读起始地址 + 写数量"是把**读区间结束位置当写起点**——规范对 Write Starting Address 无此约定（规范只是两个独立地址字段），这是设计约定，可接受，但 §5.2 未说明该约定的适用范围（如 ReadQuantity 大而 WriteQuantity 小时，回退地址落在读区间内是否合法？StartingAddress=0xFFFF + WriteQuantity=3 → 0x0002 回绕？无用例覆盖回绕）。

**影响**：低（设计约定合法），但回退公式的溢出/回绕路径未测试——StartingAddress=0xFFFF 时 0xFFFF+WriteQuantity 溢出 uint16，实现需定义回绕语义。

**修复建议**：§5.2 注明"回退公式按 uint16 模运算回绕"；新增 1 条边界用例（StartingAddress=0xFFFF, WriteQuantity=3 → WriteAddress=2）。

## 6. LOW 问题

### R2-L1：§1.3 声称"0x07, 0x08, 0x0B, 0x0C"但支持集 §8.1 为 {0x01-0x08, 0x0B, 0x0C, 0x0F-0x11, 0x14-0x18, 0x2B}——0x09/0x0A 未显式说明

**位置**：§1.3（第 33-34 行）；§8.1（第 1299 行）。

**问题**：支持集 `{0x01-0x08, 0x0B, 0x0C, 0x0F-0x11, 0x14-0x18, 0x2B}` 隐含排除 0x09、0x0A、0x0D、0x0E、0x12、0x13。规范中 0x09/0x0A/0x0D/0x0E 未定义、0x12/0x13 保留——文档未显式列出"不支持码"清单（如用户填 0x0D 的错误消息是 "unsupported function code 0x0D"，但 §8.1 未说明 0x09/0x0A 与保留码的区分）。

**影响**：低，T-053/T-053b 已覆盖 0x99，但 0x09/0x0A（与异常码 0x09/0x0A 同数值，易混淆）无用例。

### R2-L2：§11.2 R1-C4 复核行"总长 259<260 结论复核成立"与 §2.6"MBAP+PDU 最大 260"表述精确性

**位置**：§11.2（第 1633 行）。

**问题**：S13 总长 = 7(MBAP) + 253(Length 值) = 260？——不，MBAP 7 字节 + PDU 252 字节 = 259 字节，Length=253=1+252。文档写"MBAP+PDU 总长 259 < 260" ✓ 数值正确。但 §2.6"整个 Modbus TCP 报文（MBAP+PDU）最大 260 字节"与 §1.4"PDU 最大 253"组合后：7+253=260 是理论最大值，而 Length 最大 254（§2.6 声明）→ 实际报文最大 7+253=260。**PDU=253 时 Length=254，报文=260——但 S13 的 PDU=252 只到 259**。最大 PDU=253 的场景（FC 0x03 qty=125 为 252，无法达到 253；唯一 PDU=253 是 FC 0x14 响应带长数据或 FC 0x17？）文档未举任何 PDU=253 例子——上限 253 从未被用例触达（T-003 的 FC 0x01 qty=2000 → PDU=1+1+250=252 同样只到 252）。

**影响**：低，但 §2.6 声称的"PDU 最大 253"没有任何用例验证其边界值；若实现边界为 `>253 拒绝` 则 252/253 之间无测试。

### R2-L3：T-048（FIFO Count=31）与 T-120（FIFO 31 寄存器）断言重复

**位置**：§7.4 T-048（第 1069 行）；§7.15 T-120（第 1206 行）。

**问题**：T-048 与 T-120 内容相同（FC 0x18 上限 31，合法）。§7.4 边界与 §7.15 专项各设一条，未标注等价关系（R1-L4 修复了 6 条重复用例的标注，但这两条重复未处理）。

### R2-L4：§7.20 矩阵"合计 152 条"与实际编号统计

**位置**：§7.20（第 1287 行）。

**问题**：T-001~T-140 + b 后缀用例 T-009b/T-024b/T-049b/T-053b/T-057b/T-060b/T-060c/T-062b/T-066b/T-066c/T-066d/T-112b = 140+12 = **152** ✓ 数量自洽。但 §11.2"重复用例标注等价后独立用例约 143 条"——标注等价的 6 条（T-098/T-099/T-100/T-102/T-103/T-103 系）与 T-049b（"与 T-102 等价"标注）后独立用例数实际为 152-7=145，文档写 143，数字对不上。
