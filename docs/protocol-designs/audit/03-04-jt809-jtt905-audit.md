## 2. JT809 审计

### 2.1 CRITICAL 问题

#### C-1：0x1002 主链路登录应答 MsgLength=15 与 22 字节固定头矛盾（设计文档 §7B.13 行 1253）

**位置**：§7B.13 hex dump 示例，行 1253-1261。

**问题**：设计文档 §3B.1（行 752-762）明确声明 JT809 消息头固定 22 字节（MsgLength 4 + MsgSN 4 + MsgId 2 + VehicleColor 1 + VehiclePlate 21），且 §3B.1 注释（行 762）强调"VehicleColor + VehiclePlate 是消息头的固定部分（不归消息体），所有 MsgId 共享"。

但 0x1002 hex dump 中 MsgLength=15（0x0f），而 15 < 22，意味着整条报文长度不足以容纳消息头，物理上不可能存在。

设计文档行 1253 的公式 `4+4+2+1+21+1+4 = 15` 算术本身错误：4+4+2+1+21=32（头）+1+4=5（体）=37，而非 15。作者将"含本字段的整条报文长度"误算为 15，实际应为 37。

```python
# 验算
header = 4 + 4 + 2 + 1 + 21  # = 32
body = 1 + 4                  # = 5 (Result + GNSSCenterId)
total = header + body         # = 37, NOT 15
```

**影响**：实现者若照抄 hex dump 的 MsgLength=0x0f，生成的 0x1002 报文长度字段声明 15 字节但实际发送 37 字节，上级平台按 MsgLength 截取前 15 字节解码，将读到不完整的 MsgSN/MsgId/VehicleColor，后续业务全部错位。这正是 CLAUDE.md 测试策略 §5"断言可观察 outcomes"反模式：测试不断言 MsgLength 实际数值，导致字节错误静默通过。

**修复**：
1. 将 0x1002 hex dump 的 MsgLength 从 `00 00 00 0f` 改为 `00 00 00 25`（37）。
2. 修正行 1253 的公式注释为 `4+4+2+1+21+1+4 = 37`。
3. B-35 测试用例（msglength_correct）必须显式断言 0x1002 MsgLength=37 而非"22+body length"模糊表述。

#### C-2：0x1200 车辆注册 hex dump 的 MsgLength 与 SubLength 三重矛盾（设计文档 §7B.13 行 1266-1279）

**位置**：§7B.13 hex dump 示例，行 1266-1279。

**问题**：0x1200 车辆注册 hex dump 存在三重长度矛盾：

1. **SubLength 与 SubBody 实际长度不符**：SubLength=0x0029=41，但 hex 中 SubBody 只展示 38 字节（Phone 6 + Mfr 5 + Model 20 + Id 7 = 38），差 3 字节。
2. **MsgLength 与子段长度和不符**：MsgLength=0x004a=74，但按 22(头) + 1(SubMsgId) + 2(SubLength) + 38(SubBody 实际) = 63，差 11 字节；即使按 SubLength=41 计算，22+1+2+41=66，仍差 8 字节。
3. **SubBody 字段与 §4B.5 声明不符**：§4B.5（行 821-826）声明 0x1201 SubBody"同 JT808 0x0100"，但 JT808 0x0100 body = ProvinceId(2) + CityId(2) + Mfr(5) + Model(20) + Id(7) + Color(1) + Plate(var)，而 hex 中 SubBody 首字段是 Phone(6 BCD)——这是 JT809 自己的字段，并非 JT808 0x0100 布局。JT809 0x1201 与 JT808 0x0100 是不同布局。

```python
# 验算
# hex 实际展示的 SubBody
subbody_hex = 6 + 5 + 20 + 7  # = 38
# SubLength 声明
sublength_claim = 41
# MsgLength 声明
msglength_claim = 74
# 按 hex 实际算
msglength_from_hex = 22 + 1 + 2 + 38  # = 63
# 按 SubLength 算
msglength_from_sublength = 22 + 1 + 2 + 41  # = 66
# 三者互不一致
```

**影响**：实现者按 §4B.5"同 JT808 0x0100"复用 JT808 位置消息体编码函数，会产出 ProvinceId/CityId/LicenseColor/LicensePlate 字段，但 hex dump 展示的是 Phone+Mfr+Model+Id，二者字段顺序与字段集都不同。实现者无法判断以哪个为准。若以 hex 为准，0x1201 SubBody 与 JT808 0x0100 复用宣告失败；若以字段表为准，hex dump 无法作为字节级期望（B-09 测试无法用 hexEqual 断言）。

**修复**：
1. 明确 0x1201 SubBody 的真实字段表（JT/T 809-2019 §4.2.2.1：TerminalPhone 6 BCD + TerminalModel 20 + TerminalId 7 + ...，并非 JT808 0x0100 布局）。
2. 修正 SubLength 为实际 SubBody 长度。
3. 修正 MsgLength = 22 + 1 + 2 + SubBody 实际长度。
4. 删除 §4B.5 行 826"同 JT808 0x0100"的误导性声明，改为"JT809 0x1201 自有字段布局，不复用 JT808 0x0100"。
5. B-09 测试用例必须用 `hexEqual` 全字节断言修正后的 hex。

#### C-3：0x1202 实时定位 hex dump 的 MsgLength 差 1 字节（设计文档 §7B.13 行 1284-1301）

**位置**：§7B.13 hex dump 示例，行 1284-1301。

**问题**：0x1202 实时定位 hex dump 声明 MsgLength=0x0036=54，但按字段求和：

- 消息头 22 字节（MsgLength 4 + MsgSN 4 + MsgId 2 + VehicleColor 1 + VehiclePlate 21）
- 消息体：SubMsgId(1) + SubLength(2) + SubBody(28)
  - SubBody 28 字节 = AlarmFlag(4) + StatusFlag(4) + Latitude(4) + Longitude(4) + Altitude(2) + Speed(2) + Direction(2) + Time(6)
- 总计 = 22 + 1 + 2 + 28 = **53**，而非 54

```python
# 验算
header = 22
body = 1 + 2 + 28  # SubMsgId + SubLength + SubBody = 31
total = header + body  # = 53, NOT 54
```

SubLength=0x001c=28 与 SubBody 28 字节一致（这部分正确），但 MsgLength 多算 1 字节。

**影响**：MsgLength=54 但实际发送 53 字节，上级平台按 MsgLength 读取时会多等 1 字节，导致下一条报文首字节被吞，后续全部错位。这正是 CLAUDE.md 测试策略 §5"断言可观察 outcomes"的反模式：B-35 测试若不断言 MsgLength 实际数值，1 字节差会静默通过。

**影响叠加**：C-1（0x1002 差 22 字节）+ C-2（0x1200 差 8-11 字节）+ C-3（0x1202 差 1 字节）= JT809 全部 4 段 hex dump 中 3 段 MsgLength 错误。仅 0x1001（58 字节）与 0x9001（58 字节）算术正确。

**修复**：将 0x1202 hex dump 的 MsgLength 从 `00 00 00 36` 改为 `00 00 00 35`（53）。

#### C-4：JT809 0x1002 同时充当"登录应答"与"通用应答"，但字段表无 ResponseSN（设计文档 §4B.2 + §6B.1 + §6B.3）

**位置**：§4B.2（行 793-798）、§6B.1（行 1057-1073）、§6B.3（行 1099）。

**问题**：设计文档对 0x1002 的角色存在三方矛盾：

1. **§4B.2 字段表**：0x1002 = "主链路登录应答"，字段 = Result(1) + GNSSCenterId(4)，共 5 字节，**无 ResponseSN 字段**。
2. **§6B.1 状态转移表**：`vehicle_register_await --收到 0x1002 (通用应答)--> main_logged_in`、`location_await --收到 0x1002--> main_logged_in`、`alarm_await --收到 0x1002--> main_logged_in`。这里 0x1002 被当作"通用应答"用于应答 0x1200/0x1400 等业务消息。
3. **§6B.3 状态变量**：`lastMainSentSN uint32：用于绑定 0x1002 通用应答的 ResponseSN`。但 §4B.2 的 0x1002 字段表根本没有 ResponseSN 字段！

按 JT/T 809-2019 规范：
- 0x1002 是**主链路登录应答**（UP_MAIN_LINK_LOGIN_RSP），仅用于应答 0x1001，字段 = Result(1) + GNSSCenterId(4)，无 ResponseSN。
- JT809 **没有**类似 JT808 0x8001 的"通用应答"消息。每个 0x1200 SubMsgId 子业务有自己的应答模式（部分子业务无应答，部分有专门的应答子消息）。
- 上级平台对 0x1200/0x1400 等的应答，按 JT/T 809-2019 应为 0x1300/0x9100 等，而非 0x1002。

**影响**：实现者按 §6B.1 用 0x1002 应答 0x1200，但 §4B.2 字段表无 ResponseSN，无法绑定所应答的 0x1200 流水号。真实上级平台收到 0x1200 后期待 0x1300 子业务应答或不应答，收到 0x1002 会判定为协议错误并断链。B-09/B-11/B-16 等测试用例期望"收到 0x1002 后进入 main_logged_in"，实现者要么伪造 0x1002 的 ResponseSN 字段（违反 §4B.2），要么不绑定 ResponseSN（违反 §6B.3），测试假绿。

**修复**：
1. 在 §4B.2 明确 0x1002 仅用于应答 0x1001，不用于应答 0x1200/0x1400。
2. 在 §6B.1 删除 `vehicle_register_await --收到 0x1002--> main_logged_in` 等转移，改为 `vehicle_register_await --收到 0x1300 SubMsgId=0x03 (应答)--> main_logged_in` 或 `vehicle_register_await --超时--> main_logged_in`（按 JT809 实际语义）。
3. 在 §6B.3 删除 `lastMainSentSN 用于绑定 0x1002 ResponseSN` 的声明。
4. 新增 0x1300 SubMsgId=0x03（应答）的字段表，或明确"JT809 部分子业务无应答，planner 直接进入下一状态"。

### 2.2 HIGH 问题

#### H-1：JT809 0x1001 LinkFlag 字段不存在于 JT/T 809-2019 规范（设计文档 §4B.1 行 786）

**位置**：§4B.1（行 779-790）、§4B.8（行 857-867）。

**问题**：设计为 0x1001 和 0x9001 都定义了 LinkFlag 字段（0=主链路，1=从链路，2=主从同时），但按 JT/T 809-2019：

- 0x1001 是**主链路登录请求**，仅在主链路上发送，不存在 LinkFlag 字段。
- 0x9001 是**从链路连接请求**，仅在从链路上发送，不存在 LinkFlag 字段。
- 链路由"消息发送在哪条 TCP 连接"决定，不由消息体字段决定。

设计虚构了 LinkFlag 字段，且 LinkFlag=2（主从同时）在物理上无意义——一条消息不能同时出现在两条 TCP 连接上。

**影响**：实现者按设计在 0x1001 body 中编码 LinkFlag 字节，但真实上级平台按 JT/T 809-2019 解码 0x1001 时，LinkFlag 字节会被解释为 GNSSCenterId 的高位字节（字段错位），导致 GNSSCenterId 解析错误，登录失败。B-01 测试用例期望 LinkFlag=0 字节存在，实现者照抄则真实平台拒收。

**修复**：
1. 从 §4B.1 和 §4B.8 的字段表中删除 LinkFlag 字段。
2. 链路由 Procedure.Link 字段（"main"/"slave"）决定，planner 按 Link 值路由到对应 TCP flow。
3. 修正 0x1001/0x9001 hex dump，删除 LinkFlag 字节，MsgLength 相应减 1。
4. JT809Config 中无需 LinkFlag 字段（已有 SlaveLinkEnabled bool 表达主从链路启用与否）。

#### H-2：0x1200 SubMsgId 仅覆盖 4/10，6 个子类型零测试（设计文档 §4B.5 + §8B）

**位置**：§4B.5（行 811-837）、§8B 测试用例清单（行 1325-1364）。

**问题**：§4B.5 声明 0x1200 容器消息承载 SubMsgId 0x01-0x0A 共 10 个子类型，但 §8B 测试用例仅覆盖 4 个：

| SubMsgId | 名称 | 测试用例 |
|----------|------|----------|
| 0x01 车辆注册 0x1201 | 车辆注册 | B-09, B-10 ✓ |
| 0x02 实时定位 0x1202 | 实时定位 | B-11, B-12, B-13 ✓ |
| 0x03 定位补报 0x1203 | 定位补报 | B-14, B-15 ✓ |
| 0x04 | （未命名） | **无测试** |
| 0x05 | （未命名） | **无测试** |
| 0x06 | （未命名） | **无测试** |
| 0x07 | （未命名） | **无测试** |
| 0x08 报警 0x1208 | 报警 | B-16, B-17 ✓ |
| 0x09 | （未命名） | **无测试** |
| 0x0A 车辆注销 | 车辆注销 | **无测试** |

§4B.5 行 817 列出 0x01/0x02/0x03/0x08/0x0A 五个子类型，但 0x04-0x07/0x09 五个子类型连名称都未给出。按 CLAUDE.md 测试策略 §1"每个 spec 字段至少 1 个测试"，0x04-0x07/0x09/0x0A 共 6 个子类型零测试，且 §4B.5 字段表本身就缺这 5 个子类型的 SubBody 定义。

**影响**：实现者无法实现 0x04-0x07/0x09/0x0A 子类型（字段表缺失），且无测试验证。即使实现者按 JT/T 809-2019 补全字段表，由于无测试用例，实现错误会静默通过（CLAUDE.md §1"未被测试的字段静默零值"反模式）。

**修复**：
1. 在 §4B.5 补全 0x04-0x07/0x09/0x0A 的 SubBody 字段表（按 JT/T 809-2019 §4.2.2.x）。
2. 在 §8B 新增 B-39 至 B-44 共 6 个测试用例，每个子类型至少 1 个 happy path 测试。
3. §9.1 字段覆盖审计清单行 1789"0x1200 SubMsgId 0x01-0x0A 是否每个子类型至少 1 个测试"必须全部勾选。

#### H-3：0x1300/0x1500/0x1600/0x9100/0x9600 五个容器消息零测试（设计文档 §4B.6/4B.10/4B.11/4B.12/4B.13 + §8B）

**位置**：§4B.6（行 839-845）、§4B.10（行 876-882）、§4B.11（行 884-890）、§4B.12（行 892-898）、§4B.13（行 900-906）；§8B 测试用例清单。

**问题**：设计文档定义了 5 个容器消息（0x1300 平台交互、0x1500 车辆静态信息、0x1600 车辆控制应答、0x9100 从链路平台管理、0x9600 从链路车辆控制），每个都有 SubMsgId + SubLength + SubBody 三段式结构，但 §8B 测试用例清单中**没有任何一条**测试这 5 个容器消息。

按 CLAUDE.md 测试策略 §3"每个代码路径至少 1 个测试"：5 个容器消息 = 5 个独立的 Plan 代码路径，每个都需要至少 1 个测试。§9.3 行 1808"JT809 0x1200 容器消息路径（SubMsgId + SubLength + SubBody）是否有测试"只覆盖了 0x1200，遗漏了 0x1300/0x1500/0x1600/0x9100/0x9600。

**影响**：实现者实现这 5 个容器消息的 SubMsgId/SubLength/SubBody 编码逻辑后，无测试验证。SubLength 字段是否包含 SubMsgId 自身、SubBody 字段顺序、SubMsgId 取值范围等都会静默出错。B-38 full_lifecycle_e2e 用例不涉及这 5 个容器消息（只覆盖 0x1001/0x1200/0x1400/0x1003）。

**修复**：
1. 在 §8B 新增 B-45（0x1300 平台交互 SubMsgId=0x01 查询车辆）、B-46（0x1500 车辆静态信息 SubMsgId=0x01）、B-47（0x1600 车辆控制应答 SubMsgId=0x01）、B-48（0x9100 从链路平台管理 SubMsgId=0x01）、B-49（0x9600 从链路车辆控制 SubMsgId=0x01）共 5 个测试用例。
2. §9.3 行 1808 扩展为"0x1200/0x1300/0x1500/0x1600/0x9100/0x9600 容器消息路径各有测试"。

#### H-4：0x1400 报警附件 FileUrl 最大长度 256 字节但无 GBK 编码长度上限声明（设计文档 §4B.7 行 855 + §5B 行 997）

**位置**：§4B.7（行 847-855）、§5B JT809Procedure.FileUrl（行 997）、§7B.8（行 1180-1188）。

**问题**：设计文档三处对 FileUrl 长度的声明不一致：

1. §4B.7 行 855：FileUrl = "variable，GBK"（无上限）。
2. §5B 行 997：`FileUrl string` 注释"GBK string, max 256 bytes"。
3. §7B.8 行 1187：(c) FileUrl 超长（256 字节，边界）——暗示 256 字节是上限。
4. §7B.8 行 1188：(d) FileUrl 含中文字符（GBK 编码）——但未声明中文字符占 2 字节，UTF-8 输入" example.jpg "对应 GBK 字节数可能超过 256。

问题在于：FileUrl 是 GBK 编码，UTF-8 字符串"报警图片001.jpg"（含中文"报警图片"4 个汉字 = 8 GBK 字节 + 12 ASCII = 20 字节）与用户输入的 256 字节 UTF-8 字符串（可能含 128 个汉字 = 256 UTF-8 字节 → 256 GBK 字节，正好；或 256 个汉字 = 768 UTF-8 字节 → 512 GBK 字节，超限）之间没有明确的"GBK 编码后字节长度上限"声明。

**影响**：实现者在 Validate 阶段对 FileUrl 做长度检查时，无法确定是按 UTF-8 字节还是 GBK 字节计算。若按 UTF-8 字节限制 256，GBK 编码后可能超 256（中文 URL）；若按 GBK 字节限制 256，UTF-8 输入长度上限不确定。B-20 测试用例"FileUrl=256 字节"未声明是 UTF-8 还是 GBK 字节，测试无法唯一通过。

**修复**：
1. 在 §4B.7 明确"FileUrl GBK 编码后最大 256 字节"。
2. 在 §5B JT809Procedure.FileUrl 注释改为"GBK-encoded, max 256 bytes after encoding"。
3. 在 Validate 阶段先 GBKEncode(FileUrl) 再检查 len <= 256。
4. B-20 测试用例明确：UTF-8 输入 128 个汉字（GBK 编码后 256 字节）为边界值。

#### H-5：从链路 LinkFlag=1 固定但 0x1001 LinkFlag=2（主从同时）语义未定义（设计文档 §4B.1 行 786 + §4B.8 行 864）

**位置**：§4B.1（行 786）、§4B.8（行 864）、§6B.2（行 1075-1085）。

**问题**：即便忽略 H-1 的"LinkFlag 不应存在"问题，设计内部对 LinkFlag 取值仍自相矛盾：

- §4B.1：0x1001 LinkFlag = 0=主链路登录，1=从链路登录，2=主从同时。
- §4B.8：0x9001 LinkFlag = 1=从链路（固定）。
- §6B.2：从链路状态转移表中，0x9001 是独立的从链路登录消息。

如果 0x1001 LinkFlag=2 表示"主从同时登录"，那么从链路是否还需要发 0x9001？§6B.2 状态机明确要求 0x9001 独立发送，那么 LinkFlag=2 的语义是什么？是 0x1001 一条消息同时完成主从登录？这在物理上不可能（主从链路是两条独立 TCP）。

**影响**：实现者无法处理 LinkFlag=2 的场景：是只发 0x1001 不发 0x9001？还是发 0x1001 + 0x9001？JT809Config.SlaveLinkEnabled 与 LinkFlag=2 语义重叠且冲突。B-22 测试用例"SlaveLinkEnabled=true，0x9001 Result=0"隐含 SlaveLinkEnabled 控制从链路，那 LinkFlag 字段冗余。

**修复**：
1. 配合 H-1，删除 LinkFlag 字段。
2. 若保留 LinkFlag（作为冗余信息），明确 LinkFlag=2 时不发 0x9001，否则 LinkFlag=2 与 SlaveLinkEnabled=true 冲突，Validate 拒绝。

#### H-6：多下级平台 gnssCenterId 唯一性未在 Validate 强制（设计文档 §7B.10 + §5B）

**位置**：§7B.10（行 1199-1206）、§5B JT809Config（行 911-956）。

**问题**：§7B.10 声明"M 个下级平台 = M 条主链路 TCP，每个平台独立 GNSSCenterId、独立 MsgSN"，但 §5B JT809Config 的 GNSSCenterId 字段无唯一性约束。用户在 strategies 列表中配置 M 个 platform 时，可能两个 platform 的 GNSSCenterId 相同。

按 CLAUDE.md 测试策略 §6"并发正确性必须验证"，多平台并发测试（B-25/B-26）应断言"每个 flow 的 GNSSCenterId 各异"，但 B-25/B-26 用例描述仅说"4-tuple 独立，MsgSN 互不干扰"，未断言 GNSSCenterId 各异。

更严重的是：GroupID = hash(GNSSCenterId)（§6B.3 行 1096），如果两个平台 GNSSCenterId 相同，GroupID 相同，会被路由到同一 PacketWorker，导致两条主链路 TCP 的消息串扰（CLAUDE.md §6"共享 Pacer 8x 速率"反模式的变体）。

**影响**：用户误配两个相同 GNSSCenterId 的平台时，planner 不会拒绝，但两条 TCP flow 的 MsgSN 计数器共享（因 GroupID 相同路由到同一 worker），产生消息串扰。B-25 测试不断言 GNSSCenterId 唯一性，错误配置静默通过。

**修复**：
1. 在 Validate 阶段检查：若 strategies 列表中多个 JT809Config 的 GNSSCenterId 相同，返回 ValidationErrors。
2. 或在 planner 层面，FlowID 包含 GNSSCenterId + SrcPort，即使 GNSSCenterId 相同也能区分（但这与 GroupID = hash(GNSSCenterId) 路由冲突）。
3. B-25/B-26 测试用例增加断言：每个 flow 的 GNSSCenterId 各异，且 -race 下运行。

### 2.3 MEDIUM 问题

#### M-1：0x1001 hex dump 的 UserName="TEST\0" 含 null 字节但 §4B.1 声明 ASCII（设计文档 §7B.13 行 1239）

**位置**：§7B.13 hex dump 行 1239、§4B.1 行 783。

**问题**：§4B.1 声明 UserName = "5 byte[5] ASCII"，但 hex dump 中 `54 45 53 54 00` = "TEST\0"（4 字符 + 1 null 字节）。ASCII 字符串通常不含 null（C 字符串风格），JT/T 809-2019 规范中 UserName 是 5 字节 ASCII，不足 5 字符时**右补 0x00** 还是**右补空格 0x20**？设计未明确。

§5B 行 919 注释"UserName 5 ASCII chars, default = last 5 digits of GNSSCenterId zero-padded"——"zero-padded"暗示补 0x00，但 GNSSCenterId 是数字，其"后 5 位"如"00123"补 0 后是"00123\0"还是"00123"（5 字符已满无需补）？歧义。

**影响**：实现者对"TEST"（4 字符）补 0x00 还是 0x20 不确定，Wireshark 解码显示也不同。B-32 测试用例"UserName 不足 5 字符 → 拒绝"暗示不足 5 字符时 Validate 拒绝，但 hex dump 中"TEST"是 4 字符 + null，与 B-32 矛盾。

**修复**：
1. 在 §4B.1 明确"UserName 5 字节，不足 5 字符右补 0x00"。
2. 修正 B-32 为"UserName 不足 5 字符且不补 0x00 → 拒绝"。
3. 或明确"不足 5 字符时 Validate 自动补 0x00"（与 B-32 拒绝语义矛盾，需二选一）。

#### M-2：MsgSN InitialSN=0 时首条消息 SN=0 还是 SN=1 不明确（设计文档 §6B.3 + §7B.13）

**位置**：§6B.3 行 1091-1092、§7B.13 hex dump 行 1234/1309。

**问题**：§6B.3 声明"mainMsgSN uint32，初值=InitialSN，每发一条递增"。如果 InitialSN=0（默认），第一条消息的 SN 应该是 0（初值）还是 1（递增后）？

- 0x1001 hex dump（行 1234）：MsgSN=1，暗示首条消息 SN=1（即初值=0，发前递增）。
- 0x9001 hex dump（行 1309）：MsgSN=1（从链路首条），同上。

但 §6B.3 字面意思是"初值=InitialSN，每发一条递增"，即首条消息 SN=InitialSN=0，第二条 SN=1。

B-27 测试用例"InitialSN=0xFFFFFFFE，4 条消息 SN=...FE/FF/0/1"暗示首条 SN=0xFFFFFFFE=InitialSN（即初值即首条 SN），与 hex dump 的 SN=1 矛盾。

**影响**：实现者不确定首条消息 SN 是 InitialSN 还是 InitialSN+1。B-27 期望 SN=0xFFFFFFFE，但若按 hex dump 的"首条=1"逻辑，InitialSN=0xFFFFFFFE 时首条 SN=0xFFFFFFFF，与 B-27 期望不符。

**修复**：
1. 在 §6B.3 明确"首条消息 SN=InitialSN，发送后递增；第二条 SN=InitialSN+1"。
2. 修正 0x1001/0x9001 hex dump 的 MsgSN 为 0（若 InitialSN=0）。
3. 或明确"InitialSN 默认 1"（与 hex dump 一致），并在 §5B JT809Config.InitialSN 注释中说明。

#### M-3：0x1007 主链路断开通知 ReasonCode 仅覆盖 0/2/99，缺 1（紧急）（设计文档 §4B.4 + §7B.3 + §8B）

#### C-5：0x1001 上班签到 hex dump 的 MsgBodyProps=0x0040 与实际消息体长度 82 字节矛盾（设计文档 §7C.8 行 1672）

**位置**：§7C.8 hex dump 行 1672-1685。

**问题**：0x1001 上班签到 hex dump 声明 `MsgBodyProps=0x0040 (BodyLength=64, Version=2011)`，但按 §4C.2 字段表计算消息体长度：

- DriverId(20) + DriverName(16) + LicensePlate(21) + LicenseColor(1) + OnTime(6) + VehicleModel(16) + LoadCapacity(2) = **82 字节**

0x0040 的 bits 0-9 = 0x40 = 64，但实际消息体 82 字节。正确 MsgBodyProps 应为 0x0052（82）。

更严重的是，hex dump 行 1672 的 MsgBodyProps=0x0040 还隐含 Version=2011（bits 10-12=0），但 §5C JTT905Config.Version 默认"2019"（bits 10-12=2），应编码为 0x0852（82 + 2<<10）。

```python
# 验算
body = 20 + 16 + 21 + 1 + 6 + 16 + 2  # = 82
props_2011 = body  # = 82 = 0x0052
props_2019 = body | (2 << 10)  # = 82 + 2048 = 2130 = 0x0852
# hex shows 0x0040 = 64, wrong on both body length AND version
```

**影响**：实现者照抄 hex dump 的 MsgBodyProps=0x0040，Wireshark jtt905（或 jt808）解码器读取 BodyLength=64，但实际消息体 82 字节，多出 18 字节被解码为下一条报文头，后续全部错位。Version=2011 而非 2019 也会导致版本相关字段解码错误。这正是 CLAUDE.md §5"不断言 MsgBodyProps 位编码"反模式。

**影响叠加**：C-5（0x1001 BodyLength 错误）+ C-6（0x1002 BodyLength 错误）+ C-7（0x8001 字段表与 hex 矛盾）= JTT905 全部 4 段 hex dump 中 3 段错误。

**修复**：
1. 将 0x1001 hex dump 的 MsgBodyProps 从 `00 40` 改为 `08 52`（version=2019, body=82）。
2. 若示例使用 Version=2011，则在 hex 注释中明确"示例用 2011 版本"，MsgBodyProps 改为 `00 52`。
3. C-01 测试用例必须用 `hexEqual` 全字节断言修正后的 hex。

#### C-6：0x1002 下班签退 hex dump 的 MsgBodyProps=0x0040 与实际消息体长度 74 字节矛盾（设计文档 §7C.8 行 1704）

#### C-7：0x8001 中心通用应答字段表含 Phone(6) 但 hex dump 与 JT/T 905-2014 规范都不含（设计文档 §4C.4 + §7C.8 行 1724-1733）

#### H-7：0x1002 下班签退 OffTime BCD 编码错误且多 1 字节（设计文档 §7C.8 行 1712）

**位置**：§7C.8 hex dump 行 1712。

**问题**：0x1002 hex dump 中 OffTime 字段 hex 为 `24 08 03 31 36 30 30`，共 **7 字节**，但 §4C.3 声明 OffTime = 6 字节 BCD。问题双重：

2. **编码错误**：前 3 字节 `24 08 03` 是 BCD（24/08/03），但后 4 字节 `31 36 30 30` 是 ASCII（'1'/'6'/'0'/'0'），混合编码。正确 BCD 编码 "240803160000" 应为 `24 08 03 16 00 00`（6 字节纯 BCD）。

```python

# hex: 24 08 03 31 36 30 30 (7 bytes)
# 0x24=BCD 24, 0x08=BCD 08, 0x03=BCD 03
# 0x31=ASCII '1' (NOT BCD!), 0x36=ASCII '6', 0x30=ASCII '0', 0x30=ASCII '0'
# Correct BCD for "240803160000": 24 08 03 16 00 00 (6 bytes)
```

**影响**：实现者照抄 hex dump，OffTime 字段多 1 字节且混合编码，Wireshark BCD 解码器报错。后续 Mileage/Income/PassengerCount 字段全部偏移，解码错误。C-10 测试用例"0x1002 Mileage/Income/PassengerCount 正确"若用此 hex 作期望，会因偏移而失败或假绿。

**修复**：
1. 将 0x1002 hex dump 的 OffTime 从 `24 08 03 31 36 30 30` 改为 `24 08 03 16 00 00`（6 字节 BCD）。
2. 删除行 1712 的"-> 实际"修正注释（hex 已修正）。

## 4. 共用部分审计（Part D）

### 4.1 HIGH 问题

#### H-11：互斥规则"同 FlowSpec 不能同时承载 JT808 + JT809 + JTT905"未在 Validate 强制（设计文档 §10.1 行 1861-1871）

**位置**：§10.1 types.go 注册（行 1861-1871）。

**问题**：§10.1 在 FlowSpec 追加三个指针字段：
```go
JT808  *JT808Config  `json:"jt808,omitempty"`
JT809  *JT809Config  `json:"jt809,omitempty"`
JTT905 *JTT905Config `json:"jtt905,omitempty"`
```

三个都是 `omitempty` 指针，理论上可以同时设置（FlowSpec.JT808 != nil && FlowSpec.JT809 != nil）。但 §10.1 与 §10.2（strategy_convert 映射）都未声明互斥规则：一个 FlowSpec 只能承载一个协议配置。

按 CLAUDE.md 测试策略 §2"覆盖失败路径"，应测试"用户同时配置 JT808 + JT809 → Validate 拒绝"。但 §9 全文（行 1779-1857）无此测试项，§8B/§8C 测试用例清单也无。

**影响**：用户误配 `{"jt808": {...}, "jt809": {...}}` 在同一 FlowSpec 中时，planner 不拒绝，但 Plan 行为未定义（可能 panic 或生成混合包）。这正是 CLAUDE.md §2"未注入 broken spec 验证 task 失败"反模式。

**修复**：
1. 在 FlowSpec Validate（或 strategy_convert.parseJT808Config 等）中检查：JT808/JT809/JTT905 三者至多一个非 nil，否则返回 ValidationErrors。
2. 在 §9.2 错误路径审计清单增加"JT808+JT809 / JT808+JTT905 / JT809+JTT905 同 FlowSpec → Validate 拒绝"。
3. 新增 D 类共用测试 D-11：`multi_protocol_mutex_rejected`。

#### H-12：jtcommon.XORChecksum 签名与 JT808/JTT905 校验范围语义不符（设计文档 §11.1 行 1974-1976）

**位置**：§11.1 jtcommon.XORChecksum（行 1974-1976）。

**问题**：§11.1 声明 `XORChecksum(buf []byte) byte` 计算 buf 所有字节 XOR。但 JT808/JTT905 校验范围是**消息头 MsgId 到 MsgSN（12 字节，不含消息体、不含分包信息、不含首尾标识符、不含校验字节本身）**，不是"整条报文"。

调用者必须传入正确的 12 字节范围，但 jtcommon.XORChecksum 签名不强制这一点。实现者可能误传整条报文（含消息体、校验字节），产出错误校验码。

§11.2 复用映射行 2025"XORChecksum | JT808 用 | JTT905 用"未声明调用时传入的字节范围。§11.4 测试辅助 `assertXORChecksum(t, buf, expected)` 也未约束 buf 范围。

**影响**：实现者误传整条报文给 XORChecksum，校验码错误，Wireshark 解码报"校验码错误"。D-02 测试"已知向量：MsgId=0x0100 + MsgBodyProps=0x0000 + Phone=0x000000000001 + MsgSN=0x0001 → 校验字节=已知值"仅 12 字节，未覆盖误传场景。

**修复**：
1. 在 §11.1 XORChecksum 注释明确"调用者必须传入 MsgId 到 MsgSN 的 12 字节（无分包）或 12 字节（分包时不传 PackageNum/Total）"。
2. 新增 `XORChecksumJT808Header(msg []byte) byte` 专用于 JT808/JTT905 消息头校验，内部截取前 12 字节。
3. D-02 测试增加负面用例：传入 16 字节（含消息体）→ 校验码与 12 字节不同。

### 4.2 MEDIUM 问题

#### M-10：jtcommon.PadRight 签名与 JT809/JTT905 用法不一致（设计文档 §11.1 行 2010-2011 + §11.2 行 2030）

**位置**：§11.1 PadRight（行 2010-2011）、§11.2 复用映射行 2030。

**问题**：§11.1 声明 `PadRight(s string, width int) []byte`，输入 string 输出 []byte。但：

1. JT809 VehiclePlate 是 GBK 编码后的字节，输入应为 []byte 而非 string。若调用者先 GBKEncode 得 []byte，再转 string 传给 PadRight，可能因无效 UTF-8 字节导致 string 转换问题。
2. JTT905 DriverName 同样是 GBK 字节。
3. §11.2 行 2030"PadRight | JT809 用（21 字节 VehiclePlate）| JTT905 用（16 字节 DriverName/VehicleModel, 21 字节 LicensePlate）"未声明调用顺序：先 GBKEncode 再 PadRight，还是先 PadRight 再 GBKEncode？

正确顺序应是"先 GBKEncode 得 []byte → 再 PadRight(bytes, width)"，但 PadRight 签名要求 string 输入，需改为 `PadRight(b []byte, width int) []byte` 或 `PadRightGBK(s string, width int) ([]byte, error)`（内部 GBKEncode 后填充）。

**影响**：实现者误用 PadRight（先 PadRight string 再 GBKEncode），GBK 编码后字节长度可能超过 width（如"张三"PadRight 至 16 字节得"张三"+12 空格 = 16 字符，GBK 编码后 4+12=16 字节，巧合正确；但"张三李四"PadRight 至 16 得"张三李四"+8 空格 = 12 字符，GBK 编码后 8+8=16 字节，仍正确；但若"张三李四王五"6 汉字 = 12 GBK 字节，PadRight 至 16 字符得 6 汉字 + 10 空格 = 16 字符，GBK 编码后 12+10=22 字节，超 16）。顺序错误导致长度超限。

**修复**：
1. 将 PadRight 签名改为 `PadRight(b []byte, width int) []byte`，输入已是 GBK 字节。
2. 或新增 `PadRightGBK(s string, width int) ([]byte, error)`，内部 GBKEncode 后填充。
3. §11.2 明确调用顺序：先 GBKEncode 再 PadRight。

#### M-11：D 类共用测试 10 条未覆盖 GBK 编码边界与 BCD 全 9 边界（设计文档 §11.5 行 2063-2076）

**位置**：§11.5 D 类共用测试（行 2063-2076）。

**问题**：§11.5 列出 10 条 D 类测试，但：

1. D-05 gbk_chinese_roundtrip 仅测"京A12345"往返，未覆盖纯 ASCII（每字节 < 0x80）、纯中文（每字符 2 字节）、混合、GBK 编码后超 width 的边界。
2. D-03 bcd_encode_decode_roundtrip 仅测 12 位数字往返，未覆盖全 0（"000000000000"）、全 9（"999999999999"）、含前导 0（"012345678901"）。
3. §9.9 行 1855-1857 列出"BCD 编码边界：全 0、全 9、含前导 0"和"GBK 编码边界：纯 ASCII、纯中文、混合"，但 D 类无对应用例。

按 CLAUDE.md 测试策略 §1"每个 spec 边界至少 1 个测试"，D 类缺 5+ 个边界用例。

**影响**：GBK 编码边界错误（如纯 ASCII 时 PadRight 行为）静默通过，BCD 全 0/全 9 解码错误静默通过。

**修复**：
1. 新增 D-11 `gbk_pure_ascii`（纯 ASCII PadRight 后字节长度 = 字符数）。
2. 新增 D-12 `gbk_pure_chinese`（纯中文 PadRight 后字节长度 = 2×字符数 + 空格）。
3. 新增 D-13 `bcd_all_zeros`（"000000000000" ↔ 6 字节 0x00）。
4. 新增 D-14 `bcd_all_nines`（"999999999999" ↔ 6 字节 0x99）。
5. 新增 D-15 `bcd_leading_zero`（"012345678901" ↔ 01 23 45 67 89 01）。

### 三.2 CRITICAL

#### C-3.01：PadRightGBK 填充规则与规范/hex dump 矛盾（跨协议）

- **位置**：§11.1 PadRightGBK 函数体（L2440-2452）+ §11.2 复用映射（L2472）+ §3B.1 VehiclePlate 字段表（L892）+ §4C.2 JTT905 字段表（L1704-1705）+ 全部 hex dump（L1526、L1545、L1558、L2049、L2050、L2081、L2082）
- **严重度**：CRITICAL
- **描述**：v1.1.2 H-4 修复为 JT808 引入 `PadRightSpace`（0x20 空格填充）后，未同步修正 JT809/JTT905 的 GBK 填充规则，导致三处矛盾：

  1. **§3B.1 L892 字段表**明确："VehiclePlate 车牌号，GBK，**左空格填充至 21 字节**"（0x20 填充）。
  2. **§11.2 L2472 复用映射表**却写："PadRightGBK（VehiclePlate **GBK 编码后 0x00 填充至 21 字节**）"（0x00 填充）。
  3. **所有 JT809 hex dump**（L1526 0x1001、L1545 0x1002、L1558 0x1200、L2049/L2050/L2081/L2082 JTT905）实际字节均为 `20 20 20 ...`（0x20 空格），与 §11.2 L2472 "0x00 填充"声明矛盾。

  实质上 JT809 §3B.1 字段表与 hex dump 都用 0x20 空格填充（与规范一致），但 §11.2 复用映射却指向 PadRightGBK（0x00 填充）。如果实现者按 §11.2 复用映射表生成报文，VehiclePlate 会被填充 0x00 而非 0x20，被真实平台按"非法车牌"拒收（JT/T 809-2019 §5.2 明确要求左对齐空格填充）。

  同理，JTT905 DriverName/VehicleModel/LicensePlate 在 §11.2 L2472 也指向 PadRightGBK（0x00 填充），但 hex dump（L2049 DriverName、L2053 VehicleModel、L2050/L2082 LicensePlate）均用 0x20 空格填充。

- **依据**：JT/T 809-2019 §5.2 消息头 VehiclePlate GBK 编码、左对齐空格填充；JT/T 905-2014 §4.2 车辆动态 LicensePlate；§3B.1 L892 字段表本身；§7B.13/§7C.x hex dump 实际字节。
- **修复建议**：

  1. §11.2 L2472 JT809 行改为：`PadRightSpace（VehiclePlate GBK 编码后左对齐空格填充至 21 字节，0x20 填充）；`（与 §3B.1 L892 一致）。
  2. §11.2 L2472 JTT905 行 DriverName/VehicleModel 改为：`PadRightSpace（DriverName/VehicleModel GBK 编码后左对齐空格填充，0x20）；LicensePlate 21 字节同 JT809 PadRightSpace`。
  3. §11.1 PadRightGBK 注释（L2440-2441）补充警告："JT809/JTT905 VehiclePlate 等需左对齐 0x20 空格填充，应使用 PadRightSpace 而非 PadRightGBK"。
  4. 或者：保留 PadRightGBK 用于真正需要 0x00 填充的场景（如有），并新增 `PadLeftGBKSpace` 或在 PadRightGBK 增加填充字节参数。

  7. 同时核查 B-39 是否还应包含 FileSize 字段——§4B.5 L967-975 字段表中 0x1204 未列出 FileSize，但 B-39 描述含 FileSize(4B)，需查规范原文确认是否字段表遗漏。

#### C-3.03：JTT905 0x8001 hex dump Version=2011 与同 session 0x1001/0x1002 Version=2019 矛盾

#### H-3.02：§5C 平台侧 MsgSN 初值与 §6C.2 platformMsgSN 矛盾

### 三.6 审计结论

#### 三.6.1 是否可进入实现阶段

**结论：不可直接进入实现阶段。**

JT809/JTT905/共享部分在 v1.1.2 修复后整体质量显著提升，但本轮新发现 13 个问题（3 CRITICAL + 2 HIGH + 5 MEDIUM + 3 LOW）：

- **C-3.01（CRITICAL）**：PadRightGBK 0x00 填充与规范/hex dump 0x20 填充矛盾，会导致 JT809 VehiclePlate 与 JTT905 LicensePlate 字节填充错位，被真实平台拒收。
- **C-3.02（CRITICAL）**：B-39~B-44 测试用例描述与 §4B.5 字段表矛盾（误将外层 VehicleColor+VehiclePlate 当 SubBody 首字段），会导致测试断言错位、SubLength 计算错误。
- **C-3.03（CRITICAL）**：JTT905 0x8001 hex dump Version=2011 与同 session 0x1001/0x1002 Version=2019 矛盾，会被真实平台按"Version 不一致"拒收。
- **H-3.01（HIGH）**：JT809 0x1202 纬度未同步 M-2 修复。
- **H-3.02（HIGH）**：§5C 平台侧 MsgSN 初值与 §6C.2 platformMsgSN 矛盾。
- **M-3.01~05（MEDIUM）**：跨协议一致性缺陷（flowID 同步、Version 同步、表格格式、FileSize 字段、VehicleColor 列表）。
- **L-3.01~03（LOW）**：修订记录命名同步、hex dump 注释补全。

#### 三.6.2 建议修复顺序

| 优先级 | 问题 | 备注 |
|--------|------|------|
| P0 | C-3.01、C-3.02、C-3.03 | 3 个 CRITICAL 必须先修复，否则报文被真实平台拒收 |
| P1 | H-3.01、H-3.02 | 2 个 HIGH 影响测试有效性与状态机正确性 |
| P2 | M-3.01~05 | 5 个 MEDIUM 影响跨协议一致性与可维护性 |
| P3 | L-3.01~03 | 3 个 LOW 影响文档严谨性 |

修复后建议重新进行一轮"修复确认审计"（约 30 分钟）以确保所有问题闭环，再启动 JT809/JTT905 实现。

v1.1.2 修复了 v1.1.0/v1.1.1 中绝大部分 CRITICAL/HIGH 问题（36 个中已修复 33 个，仅 C-3.01/02/03 未闭环），本轮新发现的 13 个问题主要是修复过程中的"同步遗漏"与"修正引入的新矛盾"，未见根本性规范冲突。
