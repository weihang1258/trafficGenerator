## 1. 产出物：每个协议两份独立文档

| 文档 | 命名 | 职责 |
|---|---|---|
| **设计文档** | `NN-协议名-design.md` | 线格式、状态机、事务模型、配置结构、错误处理——回答"这个协议怎么生成、什么算错" |
| **用例文档** | `NN-协议名-testcase.md` | 机器契约（`trafficgen/test/protocol_pcap/cases/<proto>.json`）+ 用例逐条索引（含依据链标注）——回答"每条用例断什么、凭什么断" |

**两份文档独立成文**：各自能单独读懂，不允许一份抄另一份、互为摘要。

## 2. 文档依据：权威规范

- 每个协议开工前必须找到其 **RFC 或官方规范**（如 Megaco = RFC 3525/H.248、DOH = RFC 8484、OCSP = RFC 6960、CWMP = 宽带论坛 TR-069、BACnet = ASHRAE 135、HL7 官方标准、Stratum 官方文档等）。
- 字段布局、消息类型、状态流转**从规范逐条提炼，不臆造**；规范里钉死的常量、字段顺序、长度语义，设计文档标注出处章节。
- tshark 断言字段以 `tshark -G fields` + 真实 pcap 实证为准（历史教训：设计稿臆造字段名/值格式是 igmp/ospf/pim 首轮全绿的根因）。

## 3. 对抗审查：独立子代理隔离的三向交叉审计

**审查与撰写必须分离到不同执行体（subagent）隔离进行**——撰写 agent 与审查 agent 不同，审查者对撰写产物零预设、零立场，只依据规范与契约找错；同一执行体自审自稿不能算对抗审查。审查流程：

1. **撰写者（默认主 agent 亲自撰写；2026-09-01 需求方确认执行模式：除对抗审查外一切工作由主 agent 直接执行，不派子代理）**：按 §6（设计）与 §7（用例）分别写两份文档，完成后自我复核可用性（结构齐全、锚词与 ID 一致），并声明「待独立审查」。
2. **独立审查 agent（对抗者，一只或多只并行）**：持有规范与契约，**只读**检查撰写者产物（不修改任何文件）：
   - **覆盖审用例（主向）**：按规范逐项枚举可测试行为面（消息 × 字段 × 值域 × 边界 × 错误分支 × 载体 × 场景 × 交互），核对用例集是否遗漏——**遗漏 = 用例缺陷，不因设计文档未声明而豁免**（设计漏声明的按「失败用例先行」回补设计）。设计里声明的每条行为也必须有对应断言；设计写了测不了 = 设计缺陷（改设计）。
   - **依据审断言**：每条断言必须追溯到**规范原文或设计文档**（规范优先）；两份文档都找不出规范依据的断言 = 臆造。**不要求**用例与设计章节一一映射、不要求同构——用例是独立的验证体系，一条设计规格派生多条用例（不同取值/边界/载体/场景）是正常形态。
   - **规范审两份**：抽样字段回对原始 RFC/官方文档，防「两份文档自洽但一起偏离规范」。
   - 产出**结构化问题清单**（ID、位置、问题、建议修法、严重级），**禁止自己改稿**。
3. **撰写者（第二轮）**：按清单修复 → 重跑三向自检（覆盖/依据/规范） → 回复审 agent。**审 agent 复验**：清单逐条确认关闭，未关闭项继续循环。**全部关闭 = 结论 clean**。
4. 审查轮次、问题清单摘要与修复结论写入两份文档修订记录。

**防串通与串改**：审查 agent 与撰写方（主 agent）允许复用同一会话上下文交换问题清单，但审查轮次内审查 agent 的文件系统仍是只读（仅工具层面约束），且审查结论以结构化清单为准，不得口头"看过没问题"。

发现的问题按"失败用例先行"惯例修（文档阶段即先写"能证明缺陷的断言"再补设计/用例）。

## 4. 覆盖面：每个协议必过五层

| 层面 | 要求 |
|---|---|
| **功能** | 规范定义的所有消息类型/命令/状态流转都要有正例；错误处理每类至少一条负例（配置错、线格式错、状态机错、关联错、长度错、载体错，锚词驱动） |
| **性能** | 大报文跨分段（MSS）、最小/最大边界帧、字段长度上界、多流并发下的行为；设计文档给性能相关参数（帧上界、容量约束） |
| **数据场景** | 所有字段的值域：正常值、边界值（0/满值/最大长度）、编码变体（文本/二进制/base64/DER/JSON）、非法值拒绝 |
| **地址与流** | **IPv4 与 IPv6 都要覆盖**（协议本身不涉 IP 的除外，须显式声明）；**单流**基线；有**流关联**的协议（控制流派生数据流/媒体流，如 FTP、SIP 类）必须覆盖关联场景 |
| **业务** | **现网实际常用场景**优先于教科书场景；**多会话**（并发多连接，状态互不串）；**多事务**（一个连接内多笔事务，事务间有先后依赖和关联标识，驱动顺序明确） |

每个协议设计文档设"**业务场景分析**"一节，明确：该协议现网典型跑什么、事务怎么交互、生成器按什么顺序驱动。**某层确实不适用的，显式写"不适用"+理由，不许空着，也不许硬凑用例。**

五层每一层都要展开到不可再分的测试点（§7）——不是每层一两条代表例；覆盖面按本节要求核对，用例数量随行为面自然增长。

## 5. 统一术语表（所有设计/用例文档强制沿用）

> 定性说明：配置是剧本、引擎是回放者（**声明式/脚本化回放**，declarative / scripted playback）。"事件驱动"一词**不用于**整体定性——行话里它指运行时收到刺激才反应；引擎内仅自动应答（收到请求帧自动补响应）与连接边界（事件序列中源端口切换触发新连接）两处属于反应性成分。

| 术语 | 英文对照 | 定义 |
|---|---|---|
| **事件** | event | 配置里声明的一个协议动作（`events[]` 数组元素），按序回放的最小驱动单位 |
| **事件序列** | event sequence | 一个会话内按序回放的动作清单（`events[]`） |
| **事件编排会话** | scripted session | 一个 `sessions[]` 元素：自带四元组（源端口等）+ 自己的事件序列；各会话动作可完全不同 |
| **多会话展开** | multi-session expansion | `sessions[]` 数组按序**整块**回放：先跑完第 1 个会话全流程（握手→事件→挥手），再跑下一个，不交错；第二会话包号起点 = 前一会话总包数 + 1 |
| **并发会话** | concurrent sessions | `concurrent: true` 的交错/并发回放模式（例外路径，如 mms） |
| **多会话**（vs 多流） | multi-session | 多个独立连接，各自独立四元组，会话间状态不串用（modbus 设计 §6 术语区分先例） |
| **多流**（vs 多会话） | multi-flow | 一个会话**内部**的并发流 |
| **流关联** | flow correlation | **控制流派生**数据流/媒体流的**主从关系**（FTP 控制+数据、SIP 信令+媒体、TR-069 下载副连接、ONVIF 媒体流一类）；与多会话/多流不是同一维度 |
| **事务** | transaction | 连接内一次完整的请求/响应交互；**多事务** = 连接内多笔事务有先后依赖与关联标识（TID/CorrelationID 等）；**事务交互** = 后续事务依赖前序事务状态（如登录后才允许查询） |
| **对抗审查** | adversarial cross-review | §3 定义的三向交叉审计 |
| **锚词** | anchor word | 负例 `error_contains` 断言的错误信息关键词，validator 与用例契约共用 |

## 6. 设计文档细节标准：代码可生成级

设计文档必须**细到能完整指导代码生成**——达成"仅凭设计文档 + 规范，不凭猜测即可实现 builder/validator/生成器"的细节深度。缺失即文档缺陷，需按对抗审查清单补。

**逐字段规格**（针对每个消息/命令，逐条必填）：
- 字段名、类型、宽度/长度（bit/byte）、值域、默认值、缺省行为、**端序（大/小端）**、可选/必选、编码（文本/二进制/base64/DER/JSON）；
- 每个字段在**帧/报文中的字节偏移**（有固定 header 时）或解析规则（变长元素：长度前缀/TLV/NUL 终止/固定数），**每条消息的总长度公式**（含固定/可变部分，如"23B 头 + payload"式的可计算表达式）；
- 多字节字段的端序若与 payload 其它字段不同，逐字段列出（历史教训：Gnutella 三处端序混写，靠探针 A/B 实证才钉死）；
- 每个 RPC/SOA/命令的**请求与响应形状**（方向、字段、关联标识、成功/失败表示），请求-响应对的**关联规则**（transactionId/invokeID/CorrelationID/TID 的取材与配对）；
- 校验规则逐条列出（值域/长度/关联/状态机条件），**错误报告字面值**（供负例 error_contains 使用）。

**状态机规格**：状态集合、事件、转移条件、非法转移；状态与字段/事务的关联；**确定性**——同一输入必然同一输出，禁止随机/未定义行为；生成器在某状态下遇到合法/非法事件分别做什么必须写明。

**驱动与交互规格**（每条必填）：
- 事务如何交互：请求自动应答（收到什么自动补什么）、事件编排（events[] 序列）、会话状态机推进、多会话/多流/流关联（主从、driven_by 锚定关系）；
- **自动派生规则**：生成器自动补出的帧（响应/确认/握手/挥手）逐个列出触发条件与内容，不依赖隐含知识；
- 配置照此生成帧的**完整路径**（配置 → validator → builder → 事件/包），每一步的输入输出。

**性能与容量规格**：帧/报文长度上界与开销公式（如"≥上层 payload 长 + 各层头长"）、跨 MSS 分段规则（段数 = 帧长对 MSS 的上取整）、分片/重组、并发流下的行为、默认吞吐/速率边界（协议级，生成器级速率由框架已有配置项承载，不重复定义）。

## 7. 原子用例原则

**用例 = 不可再分的测试点**：一个用例只验证一个可独立判定真伪的测试点——一个字段的一个取值/编码形态、一个错误码、一个长度或值域边界、一种载体或地址族、一个状态转移、一个关联规则、一个场景分支。不可任意合并；复合流程的正确性由顺次执行多条原子用例组合覆盖，不靠单条大用例。

**职责分离（与设计文档的关系）**：

- **设计文档指定代码生成**——线格式、状态机、驱动与自动派生规则，照它实现 builder/validator/planner；
- **用例文档承担测试保障**——验证功能与性能的正确性，是独立于设计的验证体系；
- 两份文档**不互为镜像、不做一对一映射**：设计的一条规格可以派生任意多条用例（不同取值/边界/载体/场景/组合），用例数量由**可测试行为面**决定——把规范定义的消息 × 字段 × 值域 × 边界 × 错误 × 载体 × 场景全枚举展开，量级通常为**数百条**；不设数量上限或基线，也禁止为控制数量而合并测试点。

**依据链**：每条用例断言的依据首先是**规范原文**（RFC/官方规范章节），其次才是设计文档的具体化决策。用例索引表设「依据」列标注出处（如 `RFC 8484 §4.1` 或 `设计 §3.2`）供审查追溯；**不要求**用例 ID 与设计章节一一映射，**不要求** ID 顺序与设计章节顺序一致（ID 顺序 = 未来 JSON 顺序，保持稳定即可）。

- **覆盖完整性（对抗审查主战场）**：按规范逐项枚举可测试行为面，核对用例集是否遗漏规范定义的消息/字段/错误/边界/场景/交互——遗漏即缺陷，不因设计未声明而豁免（设计漏声明的按「失败用例先行」回补设计）。
- **断言可执行**：每条用例的 expect（packet_count/has_payload/fields/frames/负例 error_contains）必须写出可执行断言（字段名与值以 tshark `-G fields` 实测为准），不得写「验证长度正确」这类不可判定的说法。
- **负例纪律**：负例执行期严格只有 `expect_error, error_contains`，不得产生成功 PCAP 或假成功；逐错误分支（配置/线格式/状态机/关联/长度/载体）各至少一条，锚词与 validator 错误字面值一一对应。
- **唯一标识**：每条用例一个 ID（`<proto>_<行为>`），全仓唯一；同族用例用后缀区分取值/形态（如 `xxx_uint_min` / `xxx_uint_max` / `xxx_uint_overflow`）。

## 8. 每协议工作步骤

1. 查规范，提炼线格式 + 事务模型 + 现网场景；
2. 写设计文档（§6 代码可生成级细节）；
3. 独立写用例文档（§7 原子用例）：从规范 + 设计派生测试点全集，拆到不可再分（数百条量级）；
4. **独立子代理隔离**对抗审查（§3），修到 clean（失败用例先行）；
5. 实现 → 单测（spec 派生 + 失败路径 + observable outcome）→ 驱动校准全绿；
6. 提交：设计 + 用例 + 代码 + 清单划线，一个提交。

## 9. B6 开工顺序（建议，可调整）

按现网分量：**CWMP（TR-069）→ Megaco 合并 planner（三名合一，规范最厚先啃）→ BACnet → HL7 → DOH → ONVIF → NMEA → MMSE → EDP → 挖矿五项**（stratum / ETHMining / XMRMining / GetWork / GBT，多为 JSON-RPC 变体，放最后批量做）。

## 10. 已确认的口径

1. **"性能"落在协议能力维度**（大报文/边界/并发流）；发包速率是生成器既有配置项，不重复造。
2. **不适用层显式声明**（如 NMEA 无会话概念），写理由，不硬凑用例。
3. **设计文档与用例文档职责分离**（2026-09-01 需求方确认）：设计管代码生成、用例管测试保障，不互为镜像、不做一对一映射；对抗审查查缺失遗漏与错误，不做同构检查。
