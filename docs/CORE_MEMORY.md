# 核心记忆文档（防跑偏唯一口径）

> 维护人：用户本人单独维护。AI 默认只读，任何修改必须经用户明确指示，不许擅自改写。
> 地位：最高优先级。其他记忆、进度、跑法文档都不得与本文件冲突，冲突时以本文件为准。

## 1. 层链是唯一配置真相，旧扁平字段必须退出

- 地址只写 `ip` 层（`src`/`dst`），端口只写 `tcp`/`udp` 层（`src_port`/`dst_port`），流数量只写独立的 `flow_control`。
- 禁止 `layers` 与顶层 `src_ip`/`dst_ip`/`src_port`/`dst_port`/`count` 混用。混用示例、用例、文档都算跑偏。
- 验收分两道门，不许互相冒充：①层链能跑通；②旧格式已彻底移除（含用例改写 + 入库检查拦住旧字段）。
- 现实缺口（2026-09-09 实测）：`mapToFlowSpec` 仍先读旧字段给默认值，`applySpecToChain` 仍把旧端口写回 `tcp`/`udp` 层，`translateTerminalConfig` 仍声明旧协议配置优先。`cases/*.json` 大量双写。FTP 只有注册表层名，没有可运行的层生成器，`[ip,tcp,ftp]` 今天提交会报生成器未实现。
- **Why:** 用户明确指出目标就是把旧格式全部改掉，给出旧格式示例等于方向错误。
- **How to apply:** 给示例只给严格层链形；若代码暂不支持，必须明确标注“目标形状，今天跑不通，需先补代码”，不许拿旧形状冒充最终方案。进度汇报必须分开说“跑通了什么”和“旧字段清掉了多少”。

## 2. 策略管一种流量模板，任务管多策略合跑

- 策略 = 单一协议的一种流量模板（比如 FTP 下载模板），自带本策略的数量/速率（`flow_control`：`flows` 条数 / `bps` 速率 / `time` 时长）。
- 任务 = 把多个策略 ID 合在一起发（可同协议多模板，也可多协议），自带全任务总上限（同三种 `flow_control`）。
- 速率关系：策略先各自限速，任务再做全场封顶，任务封顶永远生效，不改写各策略自己的值。引擎任务 ID 为 `{taskID}-{strategyID}`，各策略独立桶、任务共享父桶。
- 数量关系：策略 `flows=N` = 同一模板复制 N 条流；大量同类用大 N，大量种类用多策略。`spec` 本身不管数量。
- 现实缺口：策略+任务路径每条流自动变的只有 `src_port`（不写死时 `12345+i` 防四元组碰撞；写死则会撞）。`src_ip` 按流递增、URL 参数按流变、负载按流变，在该路径今天做不到。`tuples` 的地址端口变化只在另一条批量路径生效，策略+任务路径不读它。FTP 自身也只有一个 `Commands` + 共用 `DataChannel` 模板，没有 `sessions[]`。
- **Why:** 用户纠正：这是最早定好并落地的分工，回答时把批量路径混进来属于乱说。
- **How to apply:** 讲数量必须分清“策略复制几条”与“任务一共封顶多少”；讲变化必须诚实说今天只有源端口自动变，其他按流变化是待实现，不许暗示已有。

## 3. 通用多会话事务与多流关联处理（所有协议通用）

- 多会话：用 `sessions[]`/`flows[]` 显式声明多个会话，每个会话独立 ID、独立四元组、独立生命周期。会话内是事务/操作的有序序列（如下单→支付→确认；FTP 的下载 A→查目录 B→进目录 C→续传 D；SIP 的 INVITE→ACK→BYE）。
- 单事务处理：每个事务写清四件事——前置条件（依赖哪个会话、哪一步的结果）、触发动作（发什么命令/消息）、成功分支（下一步是什么）、失败分支（重试/跳过/中断整个会话）。
- 多流关联：凡是“一条控制/信令关联一条或多条数据/媒体流”的协议，必须有显式关联字段（如 `driven_by{session,transaction,field}`），写清三件事——归属哪个会话、归属哪个事务、由哪个字段决定（如被动模式通告的端口、媒体端口、流 ID）。每个被关联流独立 ID（全局唯一，如 `parent:sub-idx`）、独立四元组、独立握手/序号/挥手。
- 时间线与交错：必须写清各流是顺序、并发还是交错。若可交错，写清调度方式（按操作顺序逐段推进、长传输分片让位、控制可中插动作如 ABOR/STAT）、包时间戳如何体现。不许用“同一模板连续重复发射”冒充编排。
- CWMP 的 `flows[] + driven_by` 是已验证范本，新协议照此补齐；当前 FTP 只有布尔开关 + 共用模板 + 子流 ID 冲突，属于未达标，需按本条重做。
- **Why:** 用户指出之前把多数据流想得太浅，且同类场景已反复喂过多次；本条把“会话—事务—多流关联”收敛为通用打法，不再逐协议重复发明。
- **How to apply:** 任何多流协议的设计文档必须含会话表、事务序列、关联关系、插入位置、时间线五件套，缺一件不开工。

## 4. 先查规范再设计，查什么、查多深写死

- 查什么（按顺序）：①连接模型（长短连接、控制/数据是否分离、谁主动建连）；②命令/消息表（每条的请求—响应、必选可选字段）；③状态机（建连—业务—释放各状态允许什么动作）；④字段表（每个字段取值、长度、字节序、默认值）；⑤错误处理表（错误码、超时、异常分支各走哪）；⑥超时与活性（空闲超时、保活、重传语义）；⑦ NAT/代理/被动模式；⑧版本/方言差异（如 IPv6 扩展、厂商方言）。
- 以什么为准：有 RFC 查 RFC（如 FTP 959、1123、9293/1122、1579、2428），注明编号+章节；无 RFC 的协议以官方规范/标准文档为准，注明文档名+章节+版本。不许用博客、二手解读代替原文。
- 找最优解必须走三路对照，不许只看规范就定方案：①规范原文（RFC/官方文档，定“必须是什么”）；②商业化软件的实际行为（定“现网真跑成什么样”，注明产品名+版本+行为出处，如官方文档、抓包、管理面截图）；③可靠开源项目的实现思路（定“别人已经验证过的走法”，注明仓库名+版本/commit+关键文件，只借鉴思路与行为，不直接搬运受限代码）。三者结论不一致时，以规范为底线、以现网行为为准绳，在设计里写清取舍理由。
- 每个关键设计决策都要有“候选方案对比表”：至少列两个真实存在的走法（含借鉴来源）、各自优劣、对性能/复杂度/兼容性的影响、最终选了哪个、为什么。不许只写一个方案自说自话，也不许把“网上搜到一段代码”当成已验证的最优解。
- 多深算够：细到每个表格行、每个字段、每个错误码，在设计文档里都有对应条目，三选一——已实现 / 明确不支持 / 不适用，不许留白。每个条目再对应至少一个测试用例。动手前先输出“规范要求 → 业务场景 → 代码现状 → 缺口”矩阵，无矩阵不开工。
- **Why:** 用户明确批评不应等投喂，且同类问题已反复出现；把深度写死才能防止“查了等于没查”。
- **How to apply:** 设计评审先看矩阵和条目覆盖表，覆盖不全打回；发现规范与实现冲突时先改实现再补用例。

## 5. 有依据设计，有错必处理，禁止编造

- 任何设计必须写明依赖（依赖哪一层、哪个前置状态、哪个外部条件）与出错处理（失败返回什么、会话继续还是中断、是否重试、超时多久）。无依赖声明、无错误分支的设计不许进入实现。
- 禁止无依据设计：没有规范条文或已确认的现网行为支撑，不许凭空定字段、定流程、定默认值。不确定的标“待确认”并写清确认方式（查哪份文档、抓哪个现网包、问谁），不许写死混入实现。
- 禁止无支撑回答：回答逻辑结论必须能指向设计文档章节或代码文件行号；指不出的直说“还不知道，需先查”，不许编造“感觉像已有”的功能。
- **Why:** 用户原话：禁止没有任何依据的设计，禁止没有任何设计或代码支持的逻辑回答。此前把批量路径能力说成策略路径能力即属此类。
- **How to apply:** 回复前自查每条结论的出处；评审时先抽查三条结论能否定位到文档/代码，定位不到整批打回。

## 6. 所有设计必须同时考虑性能

- 任何功能设计不能只写“能不能生成”，还必须同时写清性能目标、资源预算和规模边界：目标吞吐（包/秒、比特/秒）、并发会话/流数量、单流最大报文、内存上限、队列/缓冲上限、CPU 并行度，以及在 pcap 输出和真实网卡输出下分别如何验收。
- 性能设计必须结合实现路径说明依据：数据是否流式处理、是否会全量收集、每条流/每个包新增多少内存、是否共享状态、是否需要锁、限速器和多 worker 如何保持总速率正确。没有代码路径或基准数据支撑的性能数字只能标为待确认，不许写成承诺。
- 性能测试必须覆盖基线、目标规模、压力上限、长时间运行、并发交错和资源耗尽/背压场景；断言实际吞吐、延迟、内存、CPU、队列积压和丢包/失败，而不是只断言“任务没有报错”。功能正确但超过资源预算，仍视为设计不合格。
- **Why:** 用户要求所有设计同时考虑性能，避免功能方案在大量流量、多个会话和长时间运行时不可用。
- **How to apply:** 每份设计文档都必须有“性能设计与验收”一节；没有性能目标、测量方法和失败边界，不得进入代码实现或宣称完成。

## 7. 项目只维护三份权威文档

- `docs/CORE_MEMORY.md`：核心原则和协作要求，优先级最高，由用户单独维护。
- `docs/CODE_DESIGN.md`：所有代码设计的唯一维护入口，记录依据、依赖、接口、状态、递增规则、错误处理、性能设计、实现顺序和回滚方式。
- `docs/TEST_CASES.md`：所有测试设计和验收标准的唯一维护入口，记录规范/官方文档依据、原子测试点、失败路径、现网场景和性能测试。
- 以后只把这三份文档作为日常维护入口。既有协议设计、需求、审计和交接文档保留为历史参考，不自动删除，也不作为新工作的权威入口；可执行测试代码和 `cases/*.json` 是测试产物，不计为第四份文档，但必须回指 `docs/TEST_CASES.md` 的编号。
- 三份文档的关系是：核心要求定原则，代码设计定实现，测试用例定证明方式；三者不得重复维护同一份事实，冲突时按这个顺序处理。
- **Why:** 用户要求以后只维护核心记忆、代码设计、测试用例三份文档，避免多个协议文档和历史文档分叉。
- **How to apply:** 新需求先更新核心要求（如原则变化），再更新代码设计，最后更新测试用例；没有对应设计和测试条目，不得改代码或宣称完成。

## 8. 先有代码设计文档，再动代码

- 改代码/写代码前，先在 `docs/CODE_DESIGN.md` 把设计补到可执行程度：改哪几个文件、接口签名、数据结构、主流程、错误分支、性能边界、与现有逻辑的冲突点、回滚方式。
- 设计未定稿不开工；需求变了先改代码设计文档，再改实现和测试，不许代码先行、文档后补。
- **Why:** 用户要求修改和编写代码前先完善好代码设计文档，防止边写边发明、与既有架构冲突。
- **How to apply:** 开工汇报先贴代码设计条目编号和定稿结论；无设计条目的 Diff 直接打回。

## 9. 测试用例按三源生成，颗粒度拆到不可再分

- 测试用例统一登记在 `docs/TEST_CASES.md`。三源：RFC/官方文档 + `docs/CODE_DESIGN.md` + 已确认的现网行为，缺一不可。

- 三源：RFC/官方文档 + 代码设计文档双输入，缺一不可。规范的每行表格、每个字段、每个错误码，设计的每个条目，都要有对应测试用例。
- 颗粒度：拆到不可能再分——一个用例只验一个行为点，多条件组合拆成多例。修 bug 先写复现用例变红，再改代码变绿。
- 覆盖三类场景：①数据场景（正常/边界/空值/超长/非法/大小端）；②业务场景（完整操作序列、乱序、中断续作、并发交错）；③现网常用场景（主流服务端行为、NAT/代理、常见方言/版本）。
- **Why:** 用户要求颗粒度达到不可能再分，覆盖所有数据场景、业务场景、现网常用场景；此前 178 用例全绿仍漏 33 个问题的教训即源于此。
- **How to apply:** 测试评审看三件事：用例能否回指到规范行/设计条目、断言的是输出还是摆设、失败路径是否真会红。

## 10. 文档和代码改完都要评审

- 文档改完：对着规范逐条核对（改需求文档前先对照旧需求文档逐条核对），确认无遗漏、无冲突再提交。
- 代码改完：先自查（逐行走读偏移/边界/调用点/并发/泄漏），再跑构建 + vet + 相关测试（含 `-race`）；有问题修完再审一轮，修完的 fix 本身也要再审。
- 测试也要审：是否测对函数/路径、输入是否真能触发、断言的是输出还是摆设、规范行和性能指标是否全覆盖。全绿但测错等于没测。
- **Why:** 用户要求文档和代码修改后都做 review；此前已有多轮“自以为改完、实则跑偏”即缺此环。
- **How to apply:** 汇报完成前默认已走完“改→审→测→修→再审”闭环，并给出结论（如“自审 N 轮，最后一轮干净”）。

## 11. 跟用户只讲白话，技术细节进文档

- 对话先一句白话结论，再打比方解释；协议名可说但要带上下文；禁用内部编号、字节对比、`校验器/单源化/归一化`类黑话。
- 需要拍板时给两个日常选项 + 明确建议，用户看一眼能懂。
- **Why:** 用户是决策者不是细节操作者，术语堆砌等于无法验证，之前两次被误导与此有关。
- **How to apply:** 回复前自查黑话；技术证据只贴文件路径与结论，不堆原文。

## 12. 策略和任务都必须支持动态字段，静态模板不许靠复制充数

- 策略级动态：策略内所有“每流可变”字段都必须支持动态写法（fixed/inc/rand/list/pattern 五种，含 step/seed/range/list/pattern），至少覆盖 `src_ip`/`dst_ip`/`src_port`/`dst_port`，以及协议关键业务字段（如用户名、路径、负载、标识等，逐协议在代码设计里列清单）。`flows=N` 时第 i 条流按流序号确定性算出第 i 组值（rand 用 seed+序号，同序号同结果，可复现），到尾回绕；不写动态即按 fixed 沿用静态值。
- 任务级动态：任务合并多策略时，不得丢掉各策略的动态规则；任务级封顶（flows/bps/time）只做总量截断，不改写各策略的动态序列。任务本身也必须支持动态字段用于跨策略批量（如多策略共用地址池递增），语义与策略级一致。
- 静态复制不算批量：同一模板 `flows=N` 但无任何动态字段，导致 N 条完全相同四元组，这种配置必须拒绝或告警，不许静默发出 N 条重包。之前“只有 `src_port` 自动+1”属于保底防撞，不能代替真正的动态字段。
- 动态与层链的关系：动态是“值的算法”，层链是“值的住处”。动态算出的地址仍只落 `ip` 层、端口仍只落 `tcp`/`udp` 层，数量仍只走 `flow_control`；不许为动态另起一套顶层字段与 `layers` 并存。批量路径已有的 `tuples`/`group_id` 实现是参考基线，策略+任务路径必须对齐同一套语义，不许两套规则各说各话。
- **Why:** 用户指出：没有动态字段就无法批量造流，静态模板循环生成 N 条流只会得到 N 条重包；此前只做了后面的层链和用例，丢掉了最早的按流变化逻辑。
- **How to apply:** 代码设计必须逐协议列出动态字段清单与序号算法，测试必须覆盖 inc 到尾回绕、rand 同 seed 可复现、list 轮转、pattern 替换、静态复制被拒绝五类；评审时抽查一条动态结论能否定位到序号算法代码，定位不到打回。

## 13. 统一配置 schema 是机器真相，与文档同步维护

- 路径（仓库根起）：`trafficgen/schemas/v1/`
  - `defs.json`：共享定义（flow_control 封包、output_config 输出路由、dynamic_value 五种动态值、tuple_config 四元组池、group_id 跨流绑定）。
  - `strategy.json`：策略形状（mode=synth 按协议模板合成 / mode=replay 按 pcap 回放；config 平铺字段 + layers 数组 + 协议子配置；flow_control 是模板自己的封包）。
  - `task.json`：任务形状（二选一：strategy_ids 复用已有策略，或内联 batch 一次跑多类；task 的 flow_control 只做总量上限，不改写策略封包）。
  - `batch.json`：批量形状（classes[]，每类自带速率/元组/回放规格/工作绑定；replay 类必须带 replay、不收 flow_count）。
  - `layers.json`：层链形状（有序单键对象数组，外层在前；只定形状，补全/推断/字段值归 Go 管）。
  - `generated/layers.generated.json`：注册表生成表（95 层字段表：分类、依赖、字段、缺省值、范围；由 `internal/core/layers/schemagen` 从 `layers.DefaultRegistry` 生成，不许手写）。
- 入口（Go 侧唯一真相出口）：`trafficgen/internal/core/schema/`（`ValidateStrategy` 管策略建改、`ValidateTaskCreate` 管任务建/批量建/启动；形状先行、语义随后、报错文案与老接口逐字一致）。REST 建改查（strategy create/update、task create/batch/start）只调入口，不许自写形状检查；MCP 经同一入口继承（自己不再验一遍）。
- 派生（只读下游，不许反向改上游）：
  - MCP 描述：`internal/mcp/schemagen` 从 schema 的标题/说明生成五张描述表（Strategy/Task/Batch/Defs/Layers）+ 共用 Config 描述段（`schema_descriptions_generated.go`），`flowb_query_layers` 是同一注册表的实时视图；struct 标签必须是字面量，测试锁住标签与生成文本一致。
  - 前端类型：`trafficgen/tools/webgen.py` 从 schema 生成 `web/src/api/schema-types.ts`，`index.ts` 中 Strategy/FlowControlRequest/OutputConfigRequest/output_type 为纯别名、Task 为 `extends SchemaTask`（仅 stats 为 UI 附加）；后端已删的 cps/ratio 前端选项同步删除。
  - 文档索引：`docs/config-schema.md`（生成，只做索引不抄契约文字）。
- 同步规则：改配置语义先改 schema，再改派生代码与文档；层注册表变更必须重跑生成并提交生成文件；生成文件过期测试直接变红（`TestLayersGeneratedMatchesRegistry`，本地用 `go run ./internal/core/layers/schemagen` 重跑）。
- 缺失与有值的区别：键缺席走引擎缺省，显式 null 算调用方写错直接拒绝（MCP 负责省略没填的键，不发送第三态）。非法值由语义校验按历史文案拒绝。
- 与三份文档的关系：schema 不算第四份文档，它是机器契约数据源；人类日常仍只维护三份文档，schema 与三份文档互相引用不复制全文，形状冲突时以 schema 为准。
- 现状（2026-09-09）：五份形状文件齐备，生成表已提交；strategy create/update、task create/batch/start 经统一入口；MCP 描述表与前端类型已从 schema 派生；负例一致性（REST 与 MCP 同坏配置同报错）见统一入口测试。
- **Why:** 用户要求整体 schema 有唯一存放处，所有校验与接口描述都从这里出，否则七处定义会再次分叉。
- **How to apply:** 评审先查改动是否先落 schema；发现手写形状或描述与 schema 不一致，直接打回；发现后端为 null 加兼容（而不是让调用方省略键），直接打回。

## 14. 测试用例必须是可直接 MCP 调用的任务 spec，且按真实流程执行校对

- 用例即任务：每条测试用例的 spec 必须本身就是一份可直接经 MCP 建策略建任务的配置（`test/protocol_pcap/cases/*.json` 的 `spec_json` 就是策略 config，`strategy_fc` 就是策略封包），不许维护"用例一套写法、MCP 另一套写法"的两份真相；执行工具直接消费用例文件（`flowb_run_protocol_suite`），不经过任何离线等价物转译。
- 历史用例随层链迁移：旧扁平写法的存量用例必须按最新层级链/协议子配置改写后再算覆盖，历史口径（旧包数公式、旧断言字段）不许原样带进新版本；迁移时先跑一遍拿实际 pcap 再钉断言，不许照抄旧期望值。
- 真实流程三步走：调用 MCP 建任务 → 引擎真实生成（写 pcap 或接口发包抓包）→ 用 tshark 分析 pcap 逐字段校对结果。只跑离线生成器、只断言"任务没失败"、只数包数不断言字段，都不算测过。
- 负例也要走真实流程：坏配置经 MCP 提交必须被拒（错误锚词进断言），不许只测成功路径；"任务失败时报失败"和"任务失败却报成功"是同一级别的 bug。
- 断言口径以实际 pcap 为准：端口聚合类断言（distinct values）要区分 client 侧与 server 侧（server 固定端口如 21、数据通道端口会混入聚合集），子流端口派生值（如数据通道客户端口=父端口+1）要么排除要么按派生规则写进期望；写用例前先想清楚该字段在 pcap 里到底出现在哪些方向的包上。
- **Why:** 用户要求测试必须按真实链路（MCP→生成→抓包/落盘→分析校对）执行，且用例可直接复用为 MCP 任务 spec；此前出现过"单测全绿但线上服务器二进制过期导致会话/动态特性整块缺失"的假通过，只有端到端流程能拦住。
- **How to apply:** 新协议/新特性的验收 = 用例文件经 suite 工具全绿 + pcap 落盘可人工复查（默认 `/tmp/mcp-pcaps/<proto>/`）；评审用例时抽查三点——spec 是否就是 MCP 任务配置、断言是否钉到具体字段值而非只数包、负例是否有错误锚词；服务器二进制必须与代码 HEAD 同代，跑套件前先确认。
