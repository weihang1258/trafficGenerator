# 核心记忆文档（防跑偏唯一口径）

> 维护人：用户本人单独维护。AI 默认只读，任何修改必须经用户明确指示，不许擅自改写。
> 地位：最高优先级。其他记忆、进度、跑法文档都不得与本文件冲突，冲突时以本文件为准。
> 条目编号（如 9.38）只用于引用定位；本文件经用户指示由"整行打包"细化为"一条一要求"，拆分不改任何要求语义。

## 1. 层链是唯一配置真相，旧扁平字段必须退出

**配置写法**
- 1.1 地址只写 `ip` 层（`src`/`dst`）。
- 1.2 端口只写 `tcp`/`udp` 层（`src_port`/`dst_port`）。
- 1.3 流数量只写独立的 `flow_control`。

**混用禁令**
- 1.4 禁止 `layers` 与顶层 `src_ip`/`dst_ip`/`src_port`/`dst_port`/`count` 混用。
- 1.5 混用的示例、混用的用例、混用的文档都算跑偏。

**验收两道门（不许互相冒充）**
- 1.6 门①：层链能跑通。
- 1.7 门②：旧格式已彻底移除（含用例改写 + 入库检查拦住旧字段）。

**Why:** 目标就是把旧格式全部改掉，给出旧格式示例等于方向错误。

**How to apply**
- 1.8 示例只给严格层链形。
- 1.9 代码暂不支持时明确标注"目标形状，今天跑不通，需先补代码"。
- 1.10 汇报分开说"跑通了什么"和"旧字段清掉了多少"。

**顶层白名单（2026-09-19 增补，src_mac 游离教训）**
- 1.11 顶层只允许结构性键：`layers`、`flow_control` 及其家族（`group_id`/`tuples` 等数量与跨流绑定框架字段）、`output`。协议业务与承载字段（地址、端口、MAC、TTL、协议子配置等）一律住层链——1.4 的五键是例举不是全集，清单没点名的字段同样按本条判违规。
- 1.12 字段在层链中没有可住的层时，必须立项补代码给它一个可住的层，不许用"登记保留/顶层保留/豁免"写进设计条目或门表；"明确不解决"只适用于该字段根本不被消费的场景，且用例配置里必须删掉该字段。
- 1.13 门 2① 的顶层检查按白名单制执行：只放行 1.11 列名的键，其余一律红；禁列黑名单只是实现手段，漏点的键以 1.11 为准。

## 2. 策略管一种流量模板，任务管多策略合跑

**分工定义**
- 2.1 策略 = 单一协议的一种流量模板（如 FTP 下载模板），自带本策略的数量/速率（`flow_control`：`flows` 条数 / `bps` 速率 / `time` 时长）。
- 2.2 任务 = 多个策略 ID 合在一起发（可同协议多模板，也可多协议），自带全任务总上限（同三种 `flow_control`）。

**速率**
- 2.3 策略先各自限速，任务再做全场封顶；封顶永远生效，不改写各策略自己的值。
- 2.4 引擎任务 ID 为 `{taskID}-{strategyID}`，各策略独立桶、任务共享父桶。

**数量**
- 2.5 策略 `flows=N` = 同一模板复制 N 条流；大量同类用大 N，大量种类用多策略。
- 2.6 `spec` 本身不管数量。

**按流变化**
- 2.7 按流变化走动态字段（§12）。
- 2.8 未写动态时只有 `src_port` 有自动递增保底防撞（不写死时 `12345+i`，写死则会撞）。
- 2.9 其余字段按流变化必须写动态对象，不许暗示自动有。

**Why:** 这是最早定好并落地的分工，把批量路径能力混进策略路径属于乱说。

**How to apply**
- 2.10 讲数量分清"策略复制几条"与"任务封顶多少"。
- 2.11 讲变化时动态字段按 §12 说；没写动态的字段诚实说不会变。

## 3. 通用多会话事务与多流关联处理（所有协议通用）

**多会话**
- 3.1 多会话用 `sessions[]`/`flows[]` 显式声明，不许隐式。
- 3.2 每个会话独立 ID、独立四元组、独立生命周期。
- 3.3 会话内是事务/操作的有序序列（如下单→支付→确认；FTP 的下载 A→查目录 B→进目录 C→续传 D；SIP 的 INVITE→ACK→BYE）。

**单事务四件事（每个事务写清，缺一即缺口）**
- 3.4 前置条件：依赖哪个会话、哪一步的结果。
- 3.5 触发动作：发什么命令/消息。
- 3.6 成功分支：下一步是什么。
- 3.7 失败分支：重试/跳过/中断整个会话。

**多流关联**
- 3.8 凡是"一条控制/信令关联一条或多条数据/媒体流"的协议，必须有显式关联字段（如 `driven_by{session,transaction,field}`）。
- 3.9 关联字段写清三件事：归属哪个会话、归属哪个事务、由哪个字段决定（如被动模式通告的端口、媒体端口、流 ID）。
- 3.10 每个被关联流独立 ID（全局唯一，如 `parent:sub-idx`）、独立四元组、独立握手/序号/挥手。

**时间线与交错**
- 3.11 必须写清各流是顺序、并发还是交错。
- 3.12 若可交错，写清调度方式（按操作顺序逐段推进、长传输分片让位、控制可中插动作如 ABOR/STAT）与包时间戳如何体现。
- 3.13 不许用"同一模板连续重复发射"冒充编排。

**豁免边界**
- 3.14 无长连接协议：豁免 `sessions[]` 不等于豁免多流覆盖——多流并发与单包多载荷（如多 question、多 RR）各需用例。
- 3.15 无多会话结构不等于无多事务——同连接/同流内的多轮操作、非正常结束、长保活三项，每项至少一例或一立项，无例无项即缺口。

**范本**
- 3.16 CWMP 的 `flows[] + driven_by` 是已验证范本，新协议照此补齐。

**Why:** 之前把多数据流想得太浅；本条把"会话—事务—多流关联"收敛为通用打法，不再逐协议重复发明。

**How to apply**
- 3.17 任何多流协议的设计文档必须含五件套——会话表、事务序列、关联关系、插入位置、时间线——缺一件不开工。

## 4. 先查规范再设计，查什么、查多深写死

**查什么（八项，按顺序）**
- 4.1 连接模型：长短连接、控制/数据是否分离、谁主动建连。
- 4.2 命令/消息表：每条的请求—响应、必选可选字段。
- 4.3 状态机：建连—业务—释放各状态允许什么动作。
- 4.4 字段表：每个字段取值、长度、字节序、默认值。
- 4.5 错误处理表：错误码、超时、异常分支各走哪。
- 4.6 超时与活性：空闲超时、保活、重传语义。
- 4.7 NAT/代理/被动模式。
- 4.8 版本/方言差异（如 IPv6 扩展、厂商方言）。

**以什么为准**
- 4.9 有 RFC 查 RFC（如 FTP 959、1123、9293/1122、1579、2428），注明编号+章节。
- 4.10 无 RFC 的协议以官方规范/标准文档为准，注明文档名+章节+版本。
- 4.11 不许用博客、二手解读代替原文。

**三路对照（不许只看规范就定方案）**
- 4.12 规范原文（RFC/官方文档），定"必须是什么"。
- 4.13 商业化软件的实际行为，定"现网真跑成什么样"；注明产品名+版本+行为出处（如官方文档、抓包、管理面截图）。
- 4.14 可靠开源项目的实现思路，定"别人已经验证过的走法"；注明仓库名+版本/commit+关键文件；只借鉴思路与行为，不直接搬运受限代码。
- 4.15 三路结论不一致时：以规范为底线、以现网行为为准绳，在设计里写清取舍理由。

**映射与对比**
- 4.16 商业行为逐条映射到用例编号；无映射的标待确认并写清确认方式（查哪份文档、抓哪个现网包、问谁，三选一）；无映射无确认即缺口。
- 4.17 每个关键设计决策都要有"候选方案对比表"：至少列两个真实存在的走法（含借鉴来源）、各自优劣、对性能/复杂度/兼容性的影响、最终选了哪个、为什么。
- 4.18 不许只写一个方案自说自话，也不许把"网上搜到一段代码"当成已验证的最优解。

**深度与矩阵（无矩阵不开工）**
- 4.19 细到每个表格行、每个字段、每个错误码，在设计文档里都有对应条目，三选一——已实现 / 明确不支持 / 不适用，不许留白。
- 4.20 每个条目再对应至少一个测试用例。
- 4.21 动手前先输出"规范要求 → 业务场景 → 代码现状 → 缺口"矩阵。
- 4.22 矩阵须含三张子表，缺表或表中有格无结论即缺口：
  - ①命令×响应码矩阵（逐格已覆/缺失）
  - ②数据形态变体表（协议相关全部形态逐项）
  - ③商业行为→用例映射表

**Why:** 不应等投喂；把深度写死才能防止"查了等于没查"。

**How to apply**
- 4.23 设计评审先看矩阵和条目覆盖表，覆盖不全打回。
- 4.24 规范与实现冲突时先改实现再补用例。

## 5. 有依据设计，有错必处理，禁止编造

**依赖与错误处理**
- 5.1 任何设计必须写明依赖：依赖哪一层、哪个前置状态、哪个外部条件。
- 5.2 任何设计必须写明出错处理：失败返回什么、会话继续还是中断、是否重试、超时多久。
- 5.3 无依赖声明、无错误分支的设计不许进入实现。

**禁止无依据设计**
- 5.4 没有规范条文或已确认的现网行为支撑，不许凭空定字段、定流程、定默认值。
- 5.5 不确定的标"待确认"并写清确认方式（查哪份文档、抓哪个现网包、问谁），不许写死混入实现。

**禁止无支撑回答**
- 5.6 回答的逻辑结论必须能指向设计文档章节或代码文件行号。
- 5.7 指不出的直说"还不知道，需先查"，不许编造"感觉像已有"的功能。

**Why:** 禁止没有任何依据的设计，禁止没有任何设计或代码支持的逻辑回答。

**How to apply**
- 5.8 回复前自查每条结论的出处。
- 5.9 评审时先抽查三条结论能否定位到文档/代码，定位不到整批打回。

## 6. 所有设计必须同时考虑性能

**性能设计与验收**
- 6.1 任何功能设计不能只写"能不能生成"，必须同时写清性能目标、资源预算和规模边界。
- 6.2 性能指标须列全：目标吞吐（包/秒、比特/秒）、并发会话/流数量、单流最大报文、内存上限、队列/缓冲上限、CPU 并行度。
- 6.3 验收必须写两路：pcap 输出与真实网卡输出分别如何验收。

**性能依据**
- 6.4 性能设计必须结合实现路径说明依据：数据是否流式处理、是否会全量收集、每条流/每个包新增多少内存、是否共享状态、是否需要锁、限速器和多 worker 如何保持总速率正确。
- 6.5 没有代码路径或基准数据支撑的性能数字只能标为待确认，不许写成承诺。

**性能测试**
- 6.6 性能测试必须覆盖六类场景：基线、目标规模、压力上限、长时间运行、并发交错、资源耗尽/背压。
- 6.7 断言实际吞吐、延迟、内存、CPU、队列积压和丢包/失败，不许只断言"任务没有报错"。
- 6.8 功能正确但超过资源预算，仍视为设计不合格。

**Why:** 避免功能方案在大量流量、多个会话和长时间运行时不可用。

**How to apply**
- 6.9 每份设计文档都必须有"性能设计与验收"一节。
- 6.10 没有性能目标、测量方法和失败边界，不得进入代码实现或宣称完成。

## 7. 项目只维护三份权威文档

**三份文档（各自定位）**
- 7.1 `docs/CORE_MEMORY.md`：核心原则和协作要求，优先级最高，由用户单独维护。
- 7.2 `docs/CODE_DESIGN.md`：所有代码设计的唯一维护入口，记录依据、依赖、接口、状态、递增规则、错误处理、性能设计、实现顺序和回滚方式。
- 7.3 `docs/TEST_CASES.md`：所有测试设计和验收标准的唯一维护入口，记录规范/官方文档依据、原子测试点、失败路径、现网场景和性能测试。

**历史与产物**
- 7.4 既有协议设计、需求、审计和交接文档保留为历史参考，不自动删除，也不作为新工作的权威入口。
- 7.5 可执行测试代码和 `cases/*.json` 是测试产物，不计为第四份文档，但必须回指 `docs/TEST_CASES.md` 的编号。

**三者关系**
- 7.6 核心要求定原则，代码设计定实现，测试用例定证明方式。
- 7.7 三者不得重复维护同一份事实，冲突时按 7.1→7.2→7.3 顺序处理。

**Why:** 避免多个协议文档和历史文档分叉。

**How to apply**
- 7.8 新需求先更新核心要求（如原则变化），再更新代码设计，最后更新测试用例。
- 7.9 没有对应设计和测试条目，不得改代码或宣称完成。

**设计先行（补到可执行程度，八要素缺一不可）**
- 8.1 改哪几个文件。
- 8.2 接口签名。
- 8.3 数据结构。
- 8.4 主流程。
- 8.5 错误分支。
- 8.6 性能边界。
- 8.7 与现有逻辑的冲突点。
- 8.8 回滚方式。

**定稿纪律**
- 8.9 设计未定稿不开工。
- 8.10 需求变了先改代码设计文档，再改实现和测试。
- 8.11 不许代码先行、文档后补。

**Why:** 防止边写边发明、与既有架构冲突。

**How to apply**
- 8.12 开工汇报先贴代码设计条目编号和定稿结论。
- 8.13 无设计条目的 Diff 直接打回。

## 9. 测试用例按三源生成，颗粒度拆到不可再分

**登记**
- 9.1 测试用例统一登记在 `docs/TEST_CASES.md`。

**三源（缺一不可）**
- 9.2 RFC/官方文档。
- 9.3 `docs/CODE_DESIGN.md`。
- 9.4 已确认的现网行为。
- 9.5 规范的每行表格、每个字段、每个错误码，设计的每个条目，都要有对应测试用例。

**颗粒度**
- 9.6 拆到不可能再分：一个用例只验一个行为点，多条件组合拆成多例。
- 9.7 修 bug 先写复现用例变红，再改代码变绿。

**三类场景**
- 9.8 数据场景：正常/边界/空值/超长/非法/大小端。
- 9.9 业务场景：完整操作序列、乱序、中断续作、并发交错。
- 9.10 现网常用场景：主流服务端行为、NAT/代理、常见方言/版本；只验单包字段的用例集，③算缺考。
- 9.11 业务场景须含多动作组合流：至少两条，每条含三个以上不同动作，少于两条即缺口。

**清单先行**
- 9.12 写用例前先输出全部测试点清单（规范条文→业务场景→代码分支→缺口矩阵），再逐点确认覆盖。
- 9.13 用例数量本身不是目标，清单无遗漏才是。
- 9.14 存量历史用例必须逐条审计去向（合入 / 已有等价覆盖 / 作废并注明原因），不许只搬运子集充数。

**RFC 三分类**
- 9.15 A 类：纯字符串用例，不动代码直接写。
- 9.16 B 类：需代码或解析器改动，另立项。
- 9.17 C 类：harness 或架构表达力边界，注明不做，不冒充覆盖。
- 9.18 C 类只免断言引擎内部行为；凡能用输入输出序列表达的判 A 类，归入 C 类即打回。
- 9.19 动词出现过不等于覆盖：命令—响应序列逐条对照序列矩阵；规范官方示例场景必须抄全。

**枚举取值全覆盖**
- 9.20 响应码/状态码/错误码/类型码/标志位取值表本身就是数据场景清单，每个取值至少一个用例。
- 9.21 按分支级审计：同分支下取值共享同一发包形状时可代表，但每个分支至少一例；同一码在不同命令/消息上下文出现仍算不同测试点。
- 9.22 必须扫遍该字段在配置里的所有承载位置（横幅、顶层命令/消息列表、多会话事务树等全部形状），漏扫一种形状即漏判覆盖。

**正交组合矩阵**
- 9.23 矩阵维度：模式×方向、动态策略×字段、端口推导优先级档位、地址族×结构（IPv4/IPv6 × 单会话/多会话/多流）等，已覆与缺失逐格标记。
- 9.24 地址族对称覆盖：一族已覆的格，另一族必须逐格对照补齐，缺一格即缺口，不许以一族代表另一族。
- 9.25 地址族相关的版本扩展能力、动态地址、多流同样随矩阵扩；代码尚不支持时按三分类标缺口立项，不许跳过。
- 9.26 补齐顺序：先补规范最小实现条目，再扩现网高频，最后全量。

**断言边界**
- 9.27 harness 断言做不到的（包顺序、方向、序号连续性、非常规响应文本）逐项注明。
- 9.28 不许用"字段出现过"冒充"行为顺序对"。

**补齐后必须执行全量**
- 9.29 用例文件按测试点清单补全后，必须立即经真实流程（§14）跑全量并全绿才算完成。
- 9.30 只写用例不跑、只跑增量不跑全量、跑完有红就放着，都算未完成。
- 9.31 断言数值一律以真实 pcap 校准钉死，禁止凭布局公式手算包号/端口直接写死。

**动态整格（独立维度，语义定义见 §12）**
- 9.32 凡支持动态写法的字段 × 该字段支持的每一种动态策略，逐格建用例；合法集合以代码设计文档（D-* 定稿）为准。
- 9.33 本条只锁"整格覆盖、不许抽样代表"，不许只测一两种策略就声称覆盖动态。
- 9.34 每格断言三问：①该策略宣称的语义是否在输出里真的发生；②宣称可复现的是否复现；③宣称可回绕/循环的越界时是否回绕。
- 9.35 锚点选"随流变化的可观察输出"钉住流身份；无字段可锚时降级兜底并注明。
- 9.36 真实代码尚不支持某格时：按三分类标 B/C 缺口钉现状（负例或现状断言 + 注记修复后重校准），不许删用例也不许冒充已覆盖。

**通用陷阱（写用例前自查）**
- 9.37 派生编号撞车：子流/数据通道端口=父端口+1 之类的派生规则会与相邻编号实体撞号，显式端口必须拉开间隔。
- 9.38 聚合断言混入：distinct 类端口聚合必须排除服务端固定口与所有派生口（父子流两侧），否则聚合集必混入意外值。
- 9.39 多流×静态标量互斥：flows>1 的用例里层链四元组字段必须留空或写动态对象；静态标量会触发静态复制拒绝（这是正确行为，用例要绕开而不是抱怨）。
- 9.40 共享流序号的动态字段：按流序号解析的动态字段在同一流内多个子实体（会话）间共享同一序号得到同值，期望"每个子实体不同值"的断言必然落空，须按真实语义钉。

**Why:** 颗粒度必须达到不可能再分；此前 178 用例全绿仍漏 33 个问题的教训即源于清单缺失、序列矩阵漏覆。

**How to apply（测试评审五件事）**
- 9.41 测试点清单是否先行且无遗漏。
- 9.42 用例能否回指到规范行/设计条目。
- 9.43 断言的是输出还是摆设。
- 9.44 失败路径是否真会红。
- 9.45 全量跑完是否全绿（增量全绿不算完成）。

## 10. 文档和代码改完都要评审

**文档评审**
- 10.1 文档改完：对着规范逐条核对，确认无遗漏、无冲突再提交。
- 10.2 改需求文档前，先对照旧需求文档逐条核对。

**代码评审**
- 10.3 代码改完先自查：逐行走读偏移、边界、调用点、并发、泄漏。
- 10.4 自查后再跑构建 + vet + 相关测试（含 `-race`）。
- 10.5 有问题修完再审一轮，修完的 fix 本身也要再审。

**测试评审**
- 10.6 是否测对函数/路径。
- 10.7 输入是否真能触发。
- 10.8 断言的是输出还是摆设。
- 10.9 规范行和性能指标是否全覆盖。
- 10.10 全绿但测错等于没测。

**Why:** 此前已有多轮"自以为改完、实则跑偏"，缺此环。

**How to apply**
- 10.11 汇报完成前默认已走完"改→审→测→修→再审"闭环，并给出结论（如"自审 N 轮，最后一轮干净"）。

## 11. 跟用户只讲白话，技术细节进文档

**表达**
- 11.1 对话先一句白话结论，再打比方解释。
- 11.2 协议名可说，但要带上下文。
- 11.3 禁用内部编号、字节对比、"校验器/单源化/归一化"类黑话。

**拍板**
- 11.4 需要拍板时给两个日常选项 + 明确建议，用户看一眼能懂。

**Why:** 用户是决策者不是细节操作者，术语堆砌等于无法验证，之前两次被误导与此有关。

**How to apply**
- 11.5 回复前自查黑话；技术证据只贴文件路径与结论，不堆原文。

## 12. 策略和任务都必须支持动态字段，静态模板不许靠复制充数

**策略级动态**
- 12.1 策略内所有"每流可变"字段都必须支持动态写法（fixed/inc/rand/list/pattern 五种，含 step/seed/range/list/pattern 参数）。
- 12.2 动态至少覆盖 `src_ip`/`dst_ip`/`src_port`/`dst_port`。
- 12.3 协议关键业务字段（如用户名、路径、负载、标识等）逐协议在代码设计里列清单。
- 12.4 `flows=N` 时第 i 条流按流序号确定性算出第 i 组值；rand 用 seed+序号，同序号同结果，可复现；到尾回绕。
- 12.5 不写动态即按 fixed 沿用静态值。

**任务级动态**
- 12.6 任务合并多策略时，不得丢掉各策略的动态规则。
- 12.7 任务级封顶（flows/bps/time）只做总量截断，不改写各策略的动态序列。
- 12.8 任务本身也必须支持动态字段用于跨策略批量（如多策略共用地址池递增），语义与策略级一致。

**静态复制禁令**
- 12.9 同一模板 `flows=N` 但无任何动态字段、导致 N 条完全相同四元组的配置，必须拒绝或告警，不许静默发出 N 条重包。
- 12.10 "只有 `src_port` 自动+1"属于保底防撞，不能代替真正的动态字段。

**动态与层链的关系**
- 12.11 动态是"值的算法"，层链是"值的住处"：动态算出的地址仍只落 `ip` 层、端口仍只落 `tcp`/`udp` 层、数量仍只走 `flow_control`。
- 12.12 不许为动态另起一套顶层字段与 `layers` 并存。
- 12.13 批量路径已有的 `tuples`/`group_id` 实现是参考基线，策略+任务路径必须对齐同一套语义，不许两套规则各说各话。

**Why:** 没有动态字段就无法批量造流，静态模板循环生成 N 条流只会得到 N 条重包。

**How to apply**
- 12.14 代码设计必须逐协议列出动态字段清单与序号算法。
- 12.15 测试必须覆盖五类：inc 到尾回绕、rand 同 seed 可复现、list 轮转、pattern 替换、静态复制被拒绝（矩阵落点见 §9"动态整格"，不许只测一两种策略）。
- 12.16 评审时抽查一条动态结论能否定位到序号算法代码，定位不到打回。

## 13. 统一配置 schema 是机器真相，与文档同步维护

**schema 文件（仓库根起 `trafficgen/schemas/v1/`）**
- 13.1 `defs.json`：共享定义（flow_control 封包、output_config 输出路由、dynamic_value 五种动态值、tuple_config 四元组池、group_id 跨流绑定）。
- 13.2 `strategy.json`：策略形状（mode=synth 按协议模板合成 / mode=replay 按 pcap 回放；config 平铺字段 + layers 数组 + 协议子配置；flow_control 是模板自己的封包）。
- 13.3 `task.json`：任务形状（二选一：strategy_ids 复用已有策略，或内联 batch 一次跑多类；task 的 flow_control 只做总量上限，不改写策略封包）。
- 13.4 `batch.json`：批量形状（classes[]，每类自带速率/元组/回放规格/工作绑定；replay 类必须带 replay、不收 flow_count）。
- 13.5 `layers.json`：层链形状（有序单键对象数组，外层在前；只定形状，补全/推断/字段值归 Go 管）。
- 13.6 `generated/layers.generated.json`：注册表生成表（95 层字段表：分类、依赖、字段、缺省值、范围）；由 `internal/core/layers/schemagen` 从 `layers.DefaultRegistry` 生成，不许手写。

**校验入口（Go 侧唯一真相出口 `trafficgen/internal/core/schema/`）**
- 13.7 `ValidateStrategy` 管策略建改；`ValidateTaskCreate` 管任务建/批量建/启动。
- 13.8 形状先行、语义随后，报错文案与老接口逐字一致。
- 13.9 REST 建改查（strategy create/update、task create/batch/start）只调入口，不许自写形状检查。
- 13.10 MCP 经同一入口继承，自己不再验一遍。

**派生（只读下游，不许反向改上游）**
- 13.11 MCP 描述：`internal/mcp/schemagen` 从 schema 的标题/说明生成五张描述表（Strategy/Task/Batch/Defs/Layers）+ 共用 Config 描述段（`schema_descriptions_generated.go`）。
- 13.12 `flowb_query_layers` 是同一注册表的实时视图。
- 13.13 struct 标签必须是字面量，测试锁住标签与生成文本一致。
- 13.14 前端类型：`trafficgen/tools/webgen.py` 从 schema 生成 `web/src/api/schema-types.ts`；`index.ts` 中 Strategy/FlowControlRequest/OutputConfigRequest/output_type 为纯别名、Task 为 `extends SchemaTask`（仅 stats 为 UI 附加）。
- 13.15 后端已删的 cps/ratio 前端选项同步删除。
- 13.16 文档索引：`docs/config-schema.md`（生成，只做索引不抄契约文字）。

**同步规则**
- 13.17 改配置语义先改 schema，再改派生代码与文档。
- 13.18 层注册表变更必须重跑生成并提交生成文件。
- 13.19 生成文件过期测试直接变红（`TestLayersGeneratedMatchesRegistry`；本地用 `go run ./internal/core/layers/schemagen` 重跑）。

**缺失与有值的区别**
- 13.20 键缺席走引擎缺省；显式 null 算调用方写错直接拒绝（MCP 负责省略没填的键，不发送第三态）。
- 13.21 非法值由语义校验按历史文案拒绝。

**与三份文档的关系**
- 13.22 schema 不算第四份文档，它是机器契约数据源；人类日常仍只维护三份文档。
- 13.23 schema 与三份文档互相引用不复制全文，形状冲突时以 schema 为准。

**Why:** 所有校验与接口描述都从一处出，否则七处定义会再次分叉。

**How to apply**
- 13.24 评审先查改动是否先落 schema。
- 13.25 发现手写形状或描述与 schema 不一致，直接打回。
- 13.26 发现后端为 null 加兼容（而不是让调用方省略键），直接打回。

## 14. 测试用例必须是可直接 MCP 调用的任务 spec，且按真实流程执行校对

**用例即任务**
- 14.1 每条测试用例的 spec 必须本身就是一份可直接经 MCP 建策略建任务的配置（`test/protocol_pcap/cases/*.json` 的 `spec_json` 就是策略 config，`strategy_fc` 就是策略封包）。
- 14.2 不许维护"用例一套写法、MCP 另一套写法"的两份真相。
- 14.3 执行工具直接消费用例文件（`flowb_run_protocol_suite`），不经过任何离线等价物转译。

**历史用例随层链迁移**
- 14.4 旧扁平写法的存量用例必须按最新层级链/协议子配置改写后再算覆盖。
- 14.5 历史口径（旧包数公式、旧断言字段）不许原样带进新版本。
- 14.6 迁移时先跑一遍拿实际 pcap 再钉断言，不许照抄旧期望值。

**真实流程三步走**
- 14.7 第一步：调用 MCP 建任务。
- 14.8 第二步：引擎真实生成（写 pcap 或接口发包抓包）。
- 14.9 第三步：用 tshark 分析 pcap 逐字段校对结果。
- 14.10 只跑离线生成器、只断言"任务没失败"、只数包数不断言字段，都不算测过。

**负例也要走真实流程**
- 14.11 坏配置经 MCP 提交必须被拒（错误锚词进断言），不许只测成功路径。
- 14.12 "任务失败时报失败"和"任务失败却报成功"是同一级别的 bug。

**断言口径以实际 pcap 为准**
- 14.13 端口聚合类断言（distinct values）要区分 client 侧与 server 侧（server 固定端口、子流派生端口会混入聚合集）。
- 14.14 子流端口派生值（如子流客户端口=父端口+1）要么排除，要么按派生规则写进期望。
- 14.15 写用例前先想清楚该字段在 pcap 里到底出现在哪些方向的包上。

**Why:** 只有端到端流程能拦住"单测全绿但线上服务器二进制过期导致特性整块缺失"的假通过。

**How to apply**
- 14.16 新协议/新特性的验收 = 用例文件经 suite 工具全绿 + pcap 落盘可人工复查（默认 `/tmp/mcp-pcaps/<proto>/`）。
- 14.17 评审用例时抽查三点：spec 是否就是 MCP 任务配置；断言是否钉到具体字段值而非只数包；负例是否有错误锚词。
- 14.18 服务器二进制必须与代码 HEAD 同代，跑套件前先确认。
- 14.19 验收标准是全量全绿，不是增量全绿——用例文件补新例后必须整个文件重跑全绿，不许只跑新增例。
- 14.20 断言的包号/端口基准从落盘 pcap（tshark）拿，不许手算。

## 15. 单协议重构三道硬门（门不过就停，不许跳过）

**门 1 开工门（P1 之前）**
- 15.1 每个协议开工前先交 §1–§14 一条一行对照表，写"本协议怎么满足 + 证据在哪"。
- 15.2 证据三选一：文档章节 / 代码行 / 用例号；写不出 = 缺口立项，不许空着开工。
- 15.3 三行强制展开，不许一句话带过：
  - §1 行：顶层旧键清单（`src_ip/dst_ip/src_port/dst_port/count` + 本协议顶层子映射），每个键写去向进哪个层/删掉，贴一个完整 `spec_json` 例子。
  - §3 行：五件套（会话表/事务序列/关联关系/插入位置/时间线），单流协议写豁免，不许空。
  - §12 行：动态字段清单（四元组 + 业务字段逐个列开哪个策略/不开的理由）+ 序号算法代码位置。

**门 2 提交门（每次提交前，跑 `trafficgen/tools/pipe_gate.sh <proto>` 四项全绿才许提交，红了就停）**
- 15.4 ①顶层旧键零残留：顶层协议子映射只允许"已登记过渡"的协议出现，且必须在 D-条目"明确不解决"里写清迁入计划，无计划=红。
- 15.5 ②用例文件全量绿：`CASE_PROTO=<proto>` 全量不是增量，负例带锚词。
- 15.6 ③二进制与 HEAD 同代：`find trafficgen -name '*.go' -newer <server-binary>` 无输出；有输出 = 先重编服务重跑。
- 15.7 ④覆盖反查绿：全量绿后先过反查再进 P6，反查红不进。

**门 3 验收门（P6）**

- 15.10 汇报用白话先一句结论（§11），再贴三道门的过门证据（对照表 + 脚本输出 + 抽查结果）。
