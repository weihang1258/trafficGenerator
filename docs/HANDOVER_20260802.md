## 0. 当前状态一句话

**TCP 抓包乱序问题已修复。** 根因：多 flow 使用相同四元组（`10.0.0.1:12345 → 20.0.0.1:80`），Wireshark 把不同连接的包合并成一条流导致分析混乱。修复方案：多 flow 时自动递增源端口（模拟真实 TCP 客户端的 ephemeral port），用户显式指定的 src_port 仍然优先。

## 1. 已完成的修复（2026-08-02）

### 1.1 问题根因分析

**用户 Wireshark 截图显示：**
- `[TCP Retransmission]`
- `[TCP Port numbers reused]`
- `[TCP Out-Of-Order]`
- `[TCP ACKed unseen segment]`

**实际验证发现：**
1. **TCP seq/ack 数学关系完全正确** — 三次握手、数据传输、四次挥手的 seq/ack 增量逻辑无误
2. **IP ID 递增** — 每个 flow 内部的 IP ID 顺序递增（如 22330, 22331, ..., 22338）
3. **包在网卡上顺序正确** — tcpdump 抓包显示包按 planner 生成顺序到达

**根因：**
- 多个 flow 使用相同的默认四元组 `10.0.0.1:12345 → 20.0.0.1:80`
- 每个 flow 的 TCP ISN（Initial Sequence Number）随机生成，不同
- Wireshark 按四元组归并流，把多个独立连接当成一条流分析
- 导致 seq/ack 不连续、重复 SYN、乱序等假象

**抓包证据（修复前）：**
```
# Flow 1: 10.0.0.1:12345 → 20.0.0.1:80, ISN=2343577568
11:54:26.096 SYN seq=2343577568
11:54:26.098 SYN-ACK seq=2042391690 ack=2343577569
...
11:54:26.098 FIN seq=2343577629

# Flow 2: 10.0.0.1:12345 → 20.0.0.1:80, ISN=3927263744 (相同四元组！)
11:54:26.128 SYN seq=3927263744 ← Wireshark 报 "Port numbers reused"
11:54:26.128 SYN-ACK seq=2207042647 ack=3927263745
...
```

### 1.2 修复方案

**核心思路：** 多 flow 时自动递增源端口，让每个 flow 有唯一的四元组。

**代码修改：**

1. **`internal/core/types.go`** — FlowSpec 新增字段：
   ```go
   // HasExplicitSrcPort tracks whether user explicitly provided src_port.
   // Used by multi-flow scenarios to auto-increment src_port only when
   // user didn't specify it (user > default rule).
   HasExplicitSrcPort bool `json:"-"`
   ```

2. **`internal/core/strategy_convert.go`** — mapToFlowSpec 设置标记：
   ```go
   // Track whether user explicitly provided src_port
   if _, ok := cfg["src_port"]; ok && cfg["src_port"] != nil {
       spec.HasExplicitSrcPort = true
   }
   ```

3. **`internal/core/worker.go`** — processTask 多 flow 自动递增：
   ```go
   // Multi-flow src_port auto-increment: when flowCount > 1 and user
   // didn't explicitly provide src_port, increment per flow to simulate
   // ephemeral ports. Prevents 4-tuple collisions that confuse Wireshark.
   spec := task.Spec
   if flowCount > 1 && !spec.HasExplicitSrcPort {
       spec.SrcPort = DefaultSrcPort + uint16(i)
   }
   ```

### 2.1 Shard Routing（已完成）

**功能：** 同源/目的 IP（不论方向）路由到相同 worker，保证同 flow 的包顺序。

**实现：**
- `computeHashKey` 使用无序四元组（min/max 排序后拼接）
- A→B 和 B→A 得到相同 hashKey
- 同一 shard 的 ConfigWorker→PacketWorker→OutputWorker 单 goroutine FIFO

**代码位置：**
- `internal/core/shard_router.go:computeHashKey`
- `internal/core/shard_router_test.go:TestComputeHashKeyBidirectionalSameKey`

**验证：** 已测试，工作正常，无需修改。

### 2.2 默认值体系（已完成）

**所有默认值集中在 `mapToFlowSpec`：**

| 字段 | 默认值 | 说明 |
|------|--------|------|
| `SrcMAC` | `02:00:00:00:00:01` | 本地管理 MAC（trafficgen 标记） |
| `DstMAC` | `02:00:00:00:00:02` | 本地管理 MAC |
| `SrcIP` | `10.0.0.1` | TEST-NET-1（不同 /24 模拟路由流） |
| `DstIP` | `20.0.0.1` | TEST-NET-1 |
| `SrcPort` | `12345` | 高位非特权端口 |
| `DstPort` | `80` | TCP/UDP/HTTP 默认；DNS 自动覆盖为 53 |
| `TTL` | `64` | |
| `DSCP` | `0x08` (CS1, TOS byte `0x20`) | trafficgen 包标记 |
| `IPFlags` | `0x02` (DF=1) | 对齐现代 OS TCP 默认 |

**规则：**
```
用户给的（含显式 0/空字符串/null） > 默认值 > 不加
```

**Presence-check helper：**
```go
if v, ok := cfg[key]; ok && v != nil {
    // 用户明确给了值，包括 0 或空字符串
} else {
    // 使用默认值
}
```

### 2.3 HTTP 默认值（已完成）

**请求侧：**
- `Host`：用户没给 → `dstIP`（IPv6 自动加 `[]` 括号）
- `Content-Length`：用户没给 + Body 非空 → `len(Body)`
- `Connection`：用户没给 → `Transactions>1` 或 `KeepAlive=true` → `keep-alive`，否则 `close`

**响应侧：**
- `Content-Type`：默认 `text/plain`（body 非空时）
- `Content-Length`：默认 `len(ResponseBody)`（body 非空时）
- `Connection`：同请求侧

**所有头部字段规则：** 用户给的 > 默认值 > 不加
